# USERDIE Digital — Backend Staging infrastructure decision brief

**Дата:** 23.11.2026  
**Основа:** `main` после PR #46, commit `0da14510d93b508c2008a4b69e31a7e75d6b106a`  
**Статус:** архитектурное предложение и предварительная оценка; выбор поставщика и бюджет не утверждены. Никакие облачные ресурсы не создавались.

## 1. Резюме и рекомендуемое направление

Для первого реального Backend Staging рекомендуется рассматривать **российского облачного провайдера и размещение всех компонентов staging в одном российском регионе**. Это снижает юридическую и операционную неопределённость для фонда, работающего с российскими заявителями и документами.

Короткий список для коммерческой и договорной проверки:

1. **Yandex Cloud** — базовый кандидат для расчёта: есть Managed PostgreSQL, отдельные тарифы по компонентам и опубликованные цены для региона Россия.
2. **Selectel** — альтернативный кандидат с Managed PostgreSQL, автоматизированным резервным копированием, размещением в российских ЦОД и публично заявленным соответствием требованиям 152-ФЗ до УЗ-1. До выбора необходимо проверить договор, актуальные сертификаты/аттестаты, границы ответственности и стоимость конкретной конфигурации.

Это не утверждение о юридическом соответствии конкретной конфигурации или о гарантированном качестве услуг. Рекламные заявления поставщика не заменяют проверку договора, документов и модели угроз.

**Решение по умолчанию для проектирования:** российский регион; архитектура без привязки к API конкретного провайдера; Yandex Cloud — ценовой ориентир, Selectel — обязательный альтернативный расчёт.

## 2. Почему не начинать с зарубежного региона

Фонд потенциально обрабатывает персональные данные граждан РФ. Часть 5 статьи 18 Федерального закона № 152-ФЗ ограничивает использование баз данных за пределами РФ при сборе персональных данных граждан РФ, с предусмотренными законом исключениями.

Поэтому зарубежный staging не следует выбирать только из-за удобства или низкой цены. Даже при синтетических данных необходимо заранее определить, какие данные, логи, резервные копии, support-дампы и метаданные будут передаваться поставщику и где они физически размещаются.

Для первого этапа предлагаем не переносить данные за пределы РФ. Staging должен использовать только синтетические записи и тестовые документы, не содержащие персональных данных, реальных идентификаторов или копий документов фонда. Перед использованием реальных данных требуется отдельное юридическое заключение и утверждённая схема локализации/трансграничной передачи.

## 3. Целевая схема staging

```text
GitHub main (approved commit)
          |
          | controlled deploy; no automatic production path
          v
   Container Registry
          |
          v
  Backend API (Node.js 22)
  private runtime network
          |
          +------ TLS ------> Managed PostgreSQL
          |                    |
          |                    +-- migration/schema-owner identity
          |                    +-- API runtime identity (non-owner)
          |                    +-- read-only inspection identity
          |
          +-----------------> Private object storage
          |                    (issued test PDFs / artifacts)
          |
          +-----------------> Central logs + metrics
                               (secrets and personal data redacted)

Operator access: MFA + least privilege + audit trail
Public website: remains on existing GitHub Pages
Production: separate account/network/secrets; no staging route
```

### Компоненты минимального этапа

| Компонент | Стартовая конфигурация | Назначение |
|---|---|---|
| API runtime | 2 vCPU, 4 GB RAM; Node.js 22 container | Изолированный backend API |
| PostgreSQL | Managed PostgreSQL, 1 узел для тестового staging; ориентир 2 vCPU / 8 GB RAM | Отдельная пустая staging-БД |
| DB storage | 50–100 GB SSD, по фактической минимальной конфигурации провайдера | Миграции 001–021, тестовые данные |
| Private object storage | 20–50 GB, без публичного доступа | Тестовые PDF и артефакты |
| Network | Private subnet, закрытый доступ к БД, ограниченный ingress к API | Сегментация и минимизация поверхности атаки |
| Secrets | Provider secret manager или эквивалент | Отдельные секреты runtime и migration |
| Backup | Автоматические DB backups + отдельная проверка восстановления | Восстановление в отдельную тестовую БД |
| Observability | Метрики, журналы, оповещения; redaction secrets | Диагностика и контроль эксплуатации |

Одноузловой PostgreSQL допустим только как экономичный staging-контур, не как отказоустойчивая production-схема. Реплики/Multi-AZ для staging можно оценить отдельно после определения целей доступности и бюджета.

## 4. Изоляция и безопасность

Обязательные технические границы:

- отдельный cloud project/account для staging, отдельная сеть и отдельные IAM-роли;
- никакого peering, маршрута, общего секрета или общей БД с Production;
- публичный доступ к PostgreSQL запрещён; API подключается к БД по приватной сети и TLS с проверкой сертификата;
- API runtime — отдельная LOGIN-роль PostgreSQL, не владелец схемы, без SUPERUSER/CREATEDB/CREATEROLE/BYPASSRLS и без ненужного членства;
- migration-owner используется только оператором для явного запуска `MIGRATIONS_ALLOW_APPLY=true npm run migrate`;
- inspection identity — read-only, отдельно от API и migration-owner;
- секреты не передаются в GitHub issues, PR, артефакты CI, frontend или логи;
- доступ операторов — MFA, минимальные полномочия, аудит действий;
- тестовые PDF и объектное хранилище — private by default; запрет публичных ACL;
- ограничить исходящий трафик API; необязательные recovery/AI-интеграции выключены до отдельной настройки;
- `PRIVACY_CONSENT_LEDGER_ENABLED=false`; реальные согласия и документы не регистрировать;
- DNS и MX существующего домена не менять. Для staging использовать временный технический hostname после отдельного согласования.

Проверить соответствие эффективных прав PostgreSQL по уже подготовленному read-only evidence pack. Не выполнять массовые GRANT/REVOKE без отдельного проверенного change plan.

## 5. Предварительная оценка расходов

### 5.1 Планировочный бюджет

Для первого staging с одним API-инстансом, одноузловой Managed PostgreSQL, небольшим private object storage, резервными копиями, логами и сетевыми расходами предлагается заложить:

**Ориентир: 10 000–18 000 ₽ в месяц.**

Это бюджетный диапазон для планирования, не оферта и не точная калькуляция. Он зависит от минимально доступной конфигурации БД, типа/объёма диска, резервного хранения, IP, логирования, исходящего трафика, НДС и условий договора. Стоимость HA-кластера с репликой будет выше.

### 5.2 Проверяемая тарифная основа Yandex Cloud

В опубликованном тарифе Managed PostgreSQL для региона Россия указаны, в частности, ставки AMD Zen 4: 1,8792 ₽ за vCPU-час и 0,5072 ₽ за GB RAM-час; сетевой SSD — 0,0218 ₽ за GB-час. Тарифы и НДС необходимо сверять с калькулятором и юридическим лицом, выставляющим счёт.

Иллюстрация только для вычислительной части одного узла PostgreSQL 2 vCPU / 8 GB RAM при 720 часах в месяце:

- вычисления: (2 × 1,8792 + 8 × 0,5072) × 720 ≈ 5 628 ₽/мес.;
- SSD 50 GB: 50 × 0,0218 × 720 ≈ 785 ₽/мес.;
- ориентир по этим двум статьям: около 6 413 ₽/мес.

Это не полный счёт: в нём не учтены API VM, диски API, объектное хранилище, резервные копии сверх включённого объёма, IP, логи и возможные дополнительные услуги. Минимально доступные классы и дисковые ограничения нужно подтвердить в калькуляторе перед заказом.

### 5.3 Selectel

Selectel публикует Managed PostgreSQL с автоматизированным резервным копированием, Point-in-time Recovery, российскими дата-центрами и заявленным соответствием 152-ФЗ до УЗ-1. Точная сумма зависит от выбранных vCPU, RAM, дисков, подсети и количества узлов; её нужно снять из калькулятора/панели и получить коммерческое подтверждение.

Сравнивать предложения следует на одинаковой конфигурации: API 2 vCPU/4 GB; PostgreSQL 2 vCPU/8 GB/50–100 GB; private storage 20–50 GB; backup retention 7–14 дней; один регион; фактические налоги и исходящий трафик.

## 6. Провайдерский due diligence до заказа

До создания ресурсов запросить и сохранить:

1. Юридическое лицо поставщика, договор, применимое право и порядок обработки данных.
2. Точное физическое местонахождение каждого ресурса: API, PostgreSQL, object storage, backups, logs, support copies.
3. DPA/поручение на обработку персональных данных и перечень субподрядчиков/субпроцессоров.
4. Документы о мерах защиты и область действия сертификатов/аттестатов; не принимать общие маркетинговые заявления как доказательство соответствия.
5. SLA, окна обслуживания, порядок уведомления об инцидентах и сроки ответа.
6. Backup policy, retention, PITR, шифрование, экспорт и фактическую стоимость восстановления.
7. IAM/MFA, журналирование административного доступа, возможность ограничить доступ персонала поставщика.
8. Условия удаления данных, выгрузки и прекращения договора.
9. Итоговую калькуляцию с налогами, IP, storage, backup, logs, network egress и поддержкой.
10. Возможность полностью удалить staging после испытаний без остаточных ресурсов и платных дисков.

## 7. План развёртывания после отдельного разрешения

| Этап | Действие | Критерий завершения |
|---|---|---|
| 0 | Утвердить провайдера, регион, договор и лимит расходов | Письменное решение владельца фонда |
| 1 | Создать изолированный проект, сеть, IAM и secret store | Проверены границы доступа; Production недоступен |
| 2 | Создать пустую PostgreSQL staging и три отдельные роли | Разделение runtime / migration / inspection подтверждено |
| 3 | Настроить TLS, API runtime, private storage и логи | Сертификат проверяется; секреты не попадают в логи |
| 4 | Применить миграции 001–021 явной командой | Checksum ledger совпадает с deployed commit |
| 5 | Запустить API и синтетические acceptance tests | Health, auth, lifecycle, ACL и PDF-потоки проходят проверки |
| 6 | Выполнить backup/restore rehearsal | Восстановление в отдельную тестовую БД подтверждено |
| 7 | Независимо проверить evidence pack | Runtime-role, TLS, triggers, ACL, backups — PASS |
| 8 | Подготовить отдельное решение о подключении UI | Никакого автоматического перехода в Production |

Если любой контроль не подтверждён, соответствующий gate остаётся **NOT VERIFIED**. Сбой или неполный вывод не трактуется как PASS.

## 8. Что остаётся за пределами текущего разрешения

Этот документ не является согласием на заказ облачных услуг. До отдельного подтверждения не выполнять:

- регистрацию платного аккаунта или принятие платной оферты от имени фонда;
- создание VM, Managed PostgreSQL, bucket, IP, registry или платных логов;
- добавление/изменение GitHub Secrets;
- выпуск staging hostname или изменение DNS/MX;
- передачу поставщику персональных данных или документов;
- применение миграций к какой-либо удалённой БД;
- подключение staging к публичному сайту или Production.

## 9. Решение, необходимое от владельца

Для перехода к provisioning нужны два утверждения:

1. **Поставщик:** Yandex Cloud или Selectel (либо иной российский провайдер после проверки).
2. **Лимит расходов:** подтвердить месячный предел; рекомендуемый планировочный диапазон — 10 000–18 000 ₽/мес. с последующей точной калькуляцией.

До этого инженерная работа продолжается в репозитории, а инфраструктура остаётся не созданной.

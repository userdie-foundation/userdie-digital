## 1. Подтверждённая архитектура

В репозитории уже существует backend на Node.js 22+ с PostgreSQL и HTTP API. Серверная часть находится в `backend/` и отделена от статического сайта `website/`.

На проверенном HEAD присутствуют миграции 001–013:
- базовые пользователи, роли, организации, программы, заявки, документы и аудит;
- сессии и история статусов;
- жизненный цикл программ и workflow/SLA;
- scoped role grants и их отзыв;
- независимые согласования;
- лимитирование входа и восстановления доступа;
- append-only аудит;
- заготовка хранения MFA.

Реализованная модель авторизации загружает principal и активные роли из серверной БД. Клиентские роли и scope не считаются доверенными. Есть глобальные роли и гранты, ограниченные программой, организацией или контуром.

## 2. Что можно переиспользовать

### Организации
Таблица `organizations` уже существует. Она содержит ID, название, тип (`foundation`, `partner`, `service_provider`), общий статус и дату создания. Это базовый справочник, но он не покрывает жизненный цикл партнёрских отношений и проверку исторических сведений.

### Роли и области доступа
`user_role_grants` уже поддерживает `scope_type = organization`. Поэтому отдельную параллельную систему прав для партнёров создавать не нужно. Однако правила авторизации для партнёрских карточек и документов ещё не добавлены.

### Согласования
Миграция 008 уже допускает `object_type = partnership` в `approval_requests`, а также запрещает согласование собственной заявки тем же пользователем. Есть независимый согласующий и append-only журнал событий согласования. Это подходящая основа для будущего двухэтапного подтверждения, но маршруты принятия решений и связывание согласования с полноценной записью партнёрства ещё не реализованы.

### Аудит
`audit_events` существует и защищён триггерами от обычных UPDATE, DELETE и TRUNCATE. Это переиспользуемая основа для аудита чувствительных операций. Триггеры не заменяют ограничение владельца БД и DDL-привилегий.

## 3. Выявленные пробелы

1. В `backend/src/server.mjs` нет API маршрутов партнёрского реестра.
2. В `backend/src/security/authorization.mjs` нет permissions для чтения, ведения, проверки и публикации партнёрских записей.
3. Таблица `organizations` не содержит исторического источника, степени достоверности, дат проверки, статуса партнёрского отношения и ответственного.
4. Таблица `documents` связана обязательным FK с `applications`; использовать её для партнёрских доказательств напрямую нельзя без нарушения предметной модели.
5. Нет отдельной истории изменения статусов партнёрства и модели доказательств, привязанной к организации/партнёрству.
6. Публичная проекция партнёров и её allowlist пока не реализованы.
7. Загрузка файлов, сканирование, выдача и скачивание файлов в backend README прямо указаны как не реализованные функции.
8. Реализация восстановления пароля не подключена к production entry point; MFA миграция является только схемой хранения, без полного механизма и enforcement. Эти ограничения нельзя обходить при запуске реальных кабинетов.

## 4. Архитектурное решение для P1

Не создавать вторую таблицу-справочник организаций.

Предлагаемая схема:
- сохранить `organizations` как единый справочник юридических/организационных субъектов;
- добавить отдельный профиль партнёрской проверки, связанный FK с `organizations`, для источника, исходного названия, нормализованного названия, статуса идентификации и дат проверки;
- завести отдельную сущность партнёрского отношения с собственным жизненным циклом (историческое, на проверке, подтверждённый исторический контакт, контакт восстановлен, действующее подтверждено, приостановлено, завершено);
- завести отдельный реестр доказательств с метаданными и ссылкой на защищённое хранилище; не привязывать его к `applications`;
- сохранять переходы статусов и решения в append-only истории;
- использовать существующие organization-scoped grants и `approval_requests` с `object_type = partnership`, добавив серверную проверку связи объекта, автора и независимого согласующего;
- публичный каталог формировать отдельной allowlist-проекцией после явного согласования.

Точные поля, ограничения, уникальность, индексы и поведение при удалении определить в миграции 014 после проверки полной модели и тестовых фикстур.

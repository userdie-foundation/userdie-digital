# USERDIE Digital — технический аудит партнёрского пространства

**Дата:** 12.11.2026  
**Ветка:** `main`  
**Проверяемый этап:** PostgreSQL SQL repository tests and internal evidence metadata API (latest commit to be confirmed by CI)  
**Область:** PostgreSQL migrations, RBAC, read-only API, approvals, audit, CI  
**Статус:** модель данных и защищённое чтение реестра реализованы; операции записи, доказательства и публичная проекция остаются закрытыми.

## 1. Подтверждённая основа

Backend на Node.js 22+ и PostgreSQL отделён от статического сайта. В `backend/migrations/` находятся миграции 001–014. Партнёрский контур использует существующий справочник `organizations`, организационные гранты доступа, независимые согласования и append-only аудит.

Миграция 014 добавляет:
- `partner_profiles` — идентификационный профиль, источник проверки и назначенного сотрудника;
- `partnerships` — отдельные отношения с жизненным циклом;
- `partnership_evidence` — метаданные доказательств без хранения файловых байтов в БД;
- `partnership_status_events` — историю переходов статусов;
- ограничение БД, запрещающее перевод в `active_confirmed` без соответствующего независимого одобренного решения.

Статус `active_confirmed` нельзя выставить только изменением поля: база проверяет тип и идентификатор согласуемого объекта, автора заявки и независимого согласующего.

## 2. Реализовано в текущем изменении

Добавлены только read-only маршруты:
- `GET /api/v1/partnerships?limit=25` — список, предел 1–50;
- `GET /api/v1/partnerships/:id` — карточка партнёрства.

Доступ к реестру:
- администратор и аудитор — по глобальной роли;
- сотрудник сопровождения — только к записям, назначенным этому сотруднику;
- партнёр — только к записям организации, указанной в точном organization-scoped grant.

Маршрут повторно проверяет полномочия на уровне каждой записи. Для отсутствующей и недоступной карточки возвращается одинаковый 404. В ответах списка и карточки скрывается внутреннее поле назначения ответственного. Ошибки БД не раскрывают внутренние сведения.

## 3. Реализовано в следующем этапе: внутренние метаданные доказательств

Добавлен маршрут `GET /api/v1/partnerships/:id/evidence`. Он требует действующую серверную сессию и отдельное разрешение `partnerships:evidence:read`: глобальные роли administrator/auditor либо case_worker, назначенный на родительскую запись. Партнёрская организационная роль не даёт доступа к доказательствам. Для отсутствующей и недоступной записи возвращается одинаковый 404.

SQL-запрос использует явный список полей и не выбирает `storage_key`; API не возвращает адреса хранилища или байты файлов. Это только метаданные для внутренней проверки, а не просмотр/скачивание документов. Добавлены HTTP-тесты на разрешённый и запрещённый доступ и PostgreSQL integration test реального SQL-запроса.

## 4. Что остаётся закрытым

1. Создание и изменение партнёрских записей.
2. Переходы статусов и подтверждение действующего партнёрства через API.
3. Чтение и скачивание доказательств, загрузка файлов, антивирусная проверка и управление защищённым хранилищем.
4. Публичный каталог партнёров и allowlist публикации.
5. Уведомления и автоматическое сопровождение партнёрского процесса.
6. Подключение партнёрского UI к API и подтверждённое production-развёртывание.

Запись в БД и UI не должны включаться до появления транзакционного маршрута, проверки полномочий, обязательного основания, аудита и отдельного согласования.

## 5. Переиспользуемые механизмы

- `organizations` остаётся единым справочником организаций; параллельная таблица организаций не создаётся.
- `user_role_grants` уже поддерживает область `organization`.
- `approval_requests` допускает `object_type = partnership` и независимого согласующего.
- `audit_events` защищён от обычных UPDATE, DELETE и TRUNCATE; эксплуатационные привилегии владельца БД всё равно должны быть ограничены.
- `partnership_status_events` защищён от UPDATE, DELETE и TRUNCATE.

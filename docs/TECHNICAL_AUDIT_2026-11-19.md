### 2. API рабочего пространства Центра оценки активов

Подтверждено по исходникам:

- API-адаптер подключён отдельным файлом `website/prototype/workspace-api.js`; он добавляется к существующему прототипу, не заменяя его.
- Пустое значение `userdie-api-origin` оставляет интерфейс в демонстрационном режиме; сетевые запросы не выполняются.
- При явно заданном origin адаптер проверяет HTTPS-origin без пути, использует `credentials: include` и не сохраняет пароль или содержимое документов в browser storage.
- Панель размещается рядом с существующей формой отчёта, а при её отсутствии использует представление активов или основной контейнер.
- Для узких экранов предусмотрена адаптация формы и заголовка через media query.

Ограничение: фактическая визуальная проверка на desktop/mobile браузере не выполнена в этой сессии. Проверка исходников и CI не заменяет визуальную приёмку.

### 3. Авторизация, роли и границы API

В проверенных обработчиках:

- защищённые запросы требуют активную серверно подтверждённую сессию и полномочия, загруженные из доверенного источника;
- изменяющие запросы проходят централизованную проверку точного `Origin`;
- credentialed CORS выдаёт только настроенный точный origin; preflight ограничен разрешёнными POST-маршрутами и заголовком Content-Type;
- список проверяющих ограничен активными независимыми утверждающими лицами, исключает самого автора и возвращает только display name и selection ID;
- действия в реестре вычисляются сервером по роли, назначению и статусу документа; интерфейс использует серверные флаги, но не является границей безопасности;
- при отказе reviewer-directory интерфейс может показать доступный реестр, не открывая создание документа без разрешения.

В рамках проверенных файлов не выявлен подтверждённый обход авторизации. Это не является заключением о полном отсутствии уязвимостей.

### 4. Жизненный цикл документов и PDF

По исходникам, контрольной документации и тестовому покрытию подтверждены следующие проектные гарантии:

- версии документа записываются отдельно, имеют SHA-256 и защищены от изменения/удаления;
- независимое согласование привязано к конкретной версии; автор не может выступать собственным проверяющим;
- выпуск ограничен согласованной версией, а конкурентная попытка выпуска контролируется транзакционной блокировкой;
- PDF выдаётся только для выпущенного документа и конкретной `issued_version_id`;
- PDF хранится в частном файловом хранилище, связан с версией и проверяется по контрольной сумме и размеру;
- доступ к PDF проверяется на сервере; повторное получение должно возвращать идентичные байты.

Проверка этих гарантий опирается на реализацию и автоматизированные тесты. Отдельный penetration test, аудит файловых прав на реально развёрнутом хранилище и проверка восстановления из резервной копии не проводились.

### 5. Staging и эксплуатационная готовность

Staging не развёрнут. Не подтверждены созданные облачные ресурсы, PostgreSQL instance, применённые migrations 001–018, secret manager, persistent private PDF volume, публичный API host или live API connection.

Перед staging требуются:

1. отдельный выбор региона/провайдера и согласование ежемесячного бюджета;
2. отдельная пустая staging PostgreSQL база, миграционная роль и отдельная непривилегированная runtime-роль;
3. проверенные TLS, точный `ALLOWED_ORIGIN`, login rate-limit HMAC secret и same-site API host/reverse proxy;
4. применение миграций только утверждённой процедурой из staging operator environment;
5. частное постоянное хранилище PDF и проверка прав доступа;
6. только синтетические учётные записи и данные;
7. проверка backup/restore, журналирования, мониторинга и rollback;
8. браузерная приёмка на desktop/mobile и end-to-end тесты.

Не менять DNS и MX записи. Не подключать публичный сайт к staging до отдельной приёмки. Не использовать данные благополучателей, доноров, сотрудников или партнёров в тестовой среде.

## Дополнительный аудит и исправления — 19 ноября 2026 года

### Найденный дефект целостности

При углублённой проверке migration 017 обнаружено, что lifecycle trigger проверял соответствие версии при смене статуса, но не запрещал некоторые прямые SQL-изменения полей `approved_version_id`, `issued_version_id`, утверждающего и реквизитов выпуска при сохранении/смене отдельных статусов. API не предоставлял такие поля для изменения, однако база данных должна обеспечивать самостоятельную защиту от обхода прикладного маршрута.

Исправлено на рабочей ветке:

- Migration 019: явный allowlist переходов статусов; блокировка изменения фактов независимого согласования после утверждения; блокировка изменения выпущенной версии, регистрационного номера и даты выпуска; запрет обходного отката выпущенного документа.
- Migration 020: метаданные PDF-артефактов защищены от UPDATE, DELETE и TRUNCATE.
- PostgreSQL integration test расширен проверками прямых SQL-попыток изменить approved/issued version, откатить выпущенный документ и изменить/удалить/очистить таблицу PDF-артефактов.
- Migration runner test обновлён для последовательности из 20 миграций.

### Дополнительные эксплуатационные ограничения

- В миграциях нет самостоятельного provisioning/grant-скрипта для непривилегированной runtime-роли PostgreSQL. Перед staging необходимо отдельно выдать минимальные права на нужные таблицы, последовательности и функции; runtime-role не должна владеть схемой/таблицами и не должна иметь DDL, TRUNCATE или права отключать триггеры.
- Cookie `__Host-userdie_session` имеет `Secure; HttpOnly; SameSite=Lax; Path=/`. Следовательно, API следует размещать на том же site (например, поддомен фонда) или за reverse proxy на том же origin. Не планировать независимый cross-site API host без отдельной переработки cookie/CSRF-модели и проверки современных ограничений third-party cookies.
- PostgreSQL integration test пропускается, если `PG_INTEGRATION_URL` не настроен. Факт запуска Backend CI сам по себе не доказывает, что integration suite реально выполнился против PostgreSQL.
- PDF route принимает HEAD, но на текущей реализации может генерировать/регистрировать PDF и добавлять audit event даже при HEAD. Это не меняет байты документа, но HEAD не должен иметь побочных эффектов; отдельное исправление/тест остаётся в списке перед production.
- Private storage требует проверки прав и владения каталога на реальном persistent volume. `mkdir(..., mode: 0700)` не гарантирует изменение прав уже существующего каталога; проверить фактические mode/owner и запретить доступ группе/прочим при staging acceptance.

## Углублённая проверка реестра согласий — 19 ноября 2026 года

### Выявленный риск на уровне базы данных

Первоначальная реализация проверяла большую часть условий в HTTP-сервисе, однако схема PostgreSQL не полностью дублировала эти инварианты. При прямой SQL-записи с привилегированной ролью, отличной от штатного API, база не гарантировала одновременно: совпадение субъекта и действующего лица для `authenticated_session`; связь отзыва именно с последним активным grant того же субъекта и той же версии документа; соответствие набора boolean-ключей утверждённому `choice_keys`; запрет повторного отзыва одного grant; отказ в grant для отозванной версии или `special_category`. Для реестра версий также отсутствовала отдельная защита от `TRUNCATE`.

Это не было подтверждённым обходом публичного API: штатный сервис уже проверял часть перечисленных условий. Но граница целостности БД была слабее заявленной модели, поэтому до эксплуатации требовалось усиление.

### Исправления в рабочей ветке

- Migration 021 дополнена DB-trigger `enforce_privacy_consent_event_integrity`: блокировка строки субъекта для сериализации событий; запрет подмены субъекта/действующего лица в режиме authenticated session; проверка существующей, опубликованной и неотозванной версии; запрет `special_category` без отдельного письменного механизма; точная сверка ключей и boolean-значений с утверждённым каталогом; проверка, что отзыв ссылается на последнее активное событие grant того же субъекта и документа.
- Добавлен уникальный частичный индекс, исключающий повторное использование одного grant в нескольких событиях отзыва.
- Добавлен `TRUNCATE`-guard для каталога версий документов.
- PostgreSQL integration test расширен негативными сценариями: несовпадающие ключи, чужой actor, чужой субъект в отзыве, повторный отзыв, grant по отозванной версии, попытка обычного session-grant для специальной категории и `TRUNCATE` каталога.

### Ограничения, которые остаются

1. DB-trigger защищает штатную модель доступа, но не является защитой от владельца БД или superuser, способного отключить триггеры/изменить схему. Перед staging runtime-role должна быть отдельной непривилегированной ролью, не владеть схемой/таблицами, не иметь DDL, `TRUNCATE`, `ALTER TABLE`, `DISABLE TRIGGER` и прав выдачи полномочий. Регистрация документов — отдельная DBA-процедура с независимой проверкой.
2. Текущий механизм не поддерживает юридически значимое письменное согласие на специальные категории и не поддерживает действия законного представителя. Эти потоки должны оставаться выключенными; нельзя обходить запрет через обычный checkbox.
3. В событии фиксируются учётная запись субъекта, версия документа через FK, выбранные флаги и время БД. Достаточность этого доказательства для конкретной цели, необходимость дополнительного доказательства показа текста/электронной подписи и правила представительства требуют отдельного юридического решения.
4. Политика сроков хранения, уничтожения и обработки требований субъекта должна быть согласована с неизменяемостью доказательств согласия и обязательными сроками хранения. Техническая append-only защита не отменяет законных обязанностей оператора.
5. Триггеры и индексы не заменяют независимый аудит привилегированной активности, резервное копирование и проверку восстановления.
6. Integration test условно пропускается, если `PG_INTEGRATION_URL` не настроен. Успех Backend CI сам по себе не подтверждает фактическое выполнение PostgreSQL integration suite.

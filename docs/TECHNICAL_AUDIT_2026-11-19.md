### 2. API рабочего пространства Центра оценки активов

Подтверждено по исходникам:

- API-адаптер подключён отдельным файлом `website/prototype/workspace-api.js`; он добавляется к существующему прототипу, не заменяя его.
- Пустое значение `userdie-api-origin` оставляет интерфейс в демонстрационном режиме; сетевые запросы не выполняются.
- При явно заданном origin адаптер проверяет HTTPS-origin без пути, использует `credentials: include` и не сохраняет пароль или содержимое документов в browser storage.
- Панель размещается рядом с существующей формой отчёта, а при её отсутствии использует представление активов или основной контейнер.
- Для узких экранов предусмотрена адаптация формы и заголовка через media query.

Ограничение: фактическая визуальная проверка на desktop/mobile браузере не выполнена в этой сессии. Проверка исходников и CI не заменяет визуальную приёмку.

### 3. Авторизация, роли и границы API

В проверенных обработчиках:

- защищённые запросы требуют активную серверно подтверждённую сессию и полномочия, загруженные из доверенного источника;
- изменяющие запросы проходят централизованную проверку точного `Origin`;
- credentialed CORS выдаёт только настроенный точный origin; preflight ограничен разрешёнными POST-маршрутами и заголовком Content-Type;
- список проверяющих ограничен активными независимыми утверждающими лицами, исключает самого автора и возвращает только display name и selection ID;
- действия в реестре вычисляются сервером по роли, назначению и статусу документа; интерфейс использует серверные флаги, но не является границей безопасности;
- при отказе reviewer-directory интерфейс может показать доступный реестр, не открывая создание документа без разрешения.

В рамках проверенных файлов не выявлен подтверждённый обход авторизации. Это не является заключением о полном отсутствии уязвимостей.

### 4. Жизненный цикл документов и PDF

По исходникам, контрольной документации и тестовому покрытию подтверждены следующие проектные гарантии:

- версии документа записываются отдельно, имеют SHA-256 и защищены от изменения/удаления;
- независимое согласование привязано к конкретной версии; автор не может выступать собственным проверяющим;
- выпуск ограничен согласованной версией, а конкурентная попытка выпуска контролируется транзакционной блокировкой;
- PDF выдаётся только для выпущенного документа и конкретной `issued_version_id`;
- PDF хранится в частном файловом хранилище, связан с версией и проверяется по контрольной сумме и размеру;
- доступ к PDF проверяется на сервере; повторное получение должно возвращать идентичные байты.

Проверка этих гарантий опирается на реализацию и автоматизированные тесты. Отдельный penetration test, аудит файловых прав на реально развёрнутом хранилище и проверка восстановления из резервной копии не проводились.

### 5. Staging и эксплуатационная готовность

Staging не развёрнут. Не подтверждены созданные облачные ресурсы, PostgreSQL instance, применённые migrations 001–018, secret manager, persistent private PDF volume, публичный API host или live API connection.

Перед staging требуются:

1. отдельный выбор региона/провайдера и согласование ежемесячного бюджета;
2. отдельная пустая staging PostgreSQL база, миграционная роль и отдельная непривилегированная runtime-роль;
3. проверенные TLS, точный `ALLOWED_ORIGIN`, login rate-limit HMAC secret и same-site API host/reverse proxy;
4. применение миграций только утверждённой процедурой из staging operator environment;
5. частное постоянное хранилище PDF и проверка прав доступа;
6. только синтетические учётные записи и данные;
7. проверка backup/restore, журналирования, мониторинга и rollback;
8. браузерная приёмка на desktop/mobile и end-to-end тесты.

Не менять DNS и MX записи. Не подключать публичный сайт к staging до отдельной приёмки. Не использовать данные благополучателей, доноров, сотрудников или партнёров в тестовой среде.

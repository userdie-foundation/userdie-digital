# USERDIE Digital — спецификация безопасного управления полномочиями

## 1. Текущее состояние

Серверный principal формируется только из действующей серверной сессии и записей БД. Scoped grants загружаются из `user_role_grants` с условием `revoked_at IS NULL`. Миграция 007 обеспечивает однократный отзыв без физического удаления и append-only историю `user_role_grant_events`.

Публичного API назначения или отзыва полномочий сейчас нет. Центральный маршрутизатор разрешает только явно реализованный PATCH статуса задачи; остальные методы записи возвращают 405 после проверки Origin. Это намеренное fail-closed состояние, его нельзя обходить прямой записью из интерфейса.

## 2. Цель следующего этапа

Реализовать отдельный административный workflow для scoped grants, не смешивая его с глобальными ролями в `user_roles`. Управление должно быть доступно только через сервер, доверенную сессию, проверку полномочий, транзакцию и неизменяемый аудит.

## 3. Допустимые назначения

| Роль | Допустимый scope | Условие |
|---|---|---|
| `case_worker` | `global` | Внутренний сотрудник с активной учётной записью |
| `program_manager` | `program` | Только существующая программа |
| `independent_approver` | `global` или `program` | Проверяющий не может быть заявителем/постановщиком того же согласования |
| `partner` | `organization` | Только активная организация типа partner |

Роли `administrator`, `auditor` и `applicant` остаются в глобальном реестре `user_roles` и не должны назначаться через endpoint scoped grants. Scope `contour` присутствует в схеме, но пока не доказано, что все защищённые маршруты проверяют его; API обязан отклонять такой scope до отдельного внедрения и тестирования.

## 4. Требования к назначению

Предполагаемый endpoint: `POST /api/v1/admin/role-grants`.

Обязательные проверки до записи:
1. Точная same-origin проверка уже действующего центрального CSRF-контроля.
2. Действующая сессия; principal получен только серверным resolver.
3. `isAuthorized(principal, "users:manage")` и глобальный grant `administrator`.
4. Повышенная аутентификация (MFA) и подтверждение недавней re-authentication. Пока MFA не внедрена и не enforced, endpoint не включать.
5. Роль и тип scope входят в allowlist; комбинация роли и scope соответствует таблице выше.
6. Целевая учётная запись существует и активна.
7. Для `program` — программа существует; для `organization` — организация существует, активна и имеет тип `partner`.
8. Запрещено назначать полномочия самому себе и назначать/повышать глобального администратора через этот endpoint.
9. Запрос содержит основание назначения ограниченной длины; клиент не может передать `granted_by`, `revoked_by`, timestamps или audit actor.

Запись выполняется в одной транзакции: вставка scoped grant с `granted_by = principal.id`, затем запись в `audit_events` с безопасными метаданными. DB trigger миграции 007 остаётся источником append-only события grant_created. При конфликте активного уникального grant — стабильный ответ 409 без деталей БД. Любая ошибка аудита откатывает назначение.

## 5. Требования к отзыву

Предполагаемый endpoint: `POST /api/v1/admin/role-grants/:id/revoke`.

- Те же проверки сессии, полномочий, MFA и re-authentication.
- Обязательная причина отзыва.
- Только переход `revoked_at: NULL → timestamp`; никаких DELETE и повторного изменения отозванной записи.
- `revoked_by` всегда берётся из доверенного principal.
- В одной транзакции обновляется grant и создаётся audit event; DB trigger создаёт append-only `grant_revoked`.
- После commit principal resolver больше не возвращает отозванный grant.
- Для отсутствующего и недоступного grant использовать одинаковый ответ, чтобы не раскрывать чужие назначения.

## 6. Разделение обязанностей

Назначение роли `independent_approver` должно требовать независимого подтверждения другим уполномоченным лицом; инициатор назначения не может подтвердить собственный запрос. Изменение глобальной роли `administrator` — отдельная процедура с двумя независимыми подтверждениями и контролируемым bootstrap; это не scoped grant.

До реализации approval workflow административный endpoint не должен самостоятельно назначать независимых проверяющих или администраторов. Если двухстороннее согласование ещё не реализовано, такие назначения отклоняются.

## 7. Обязательная тест-матрица

- Нет сессии / истекшая / отозванная сессия → 401.
- Не-admin, auditor, applicant, partner → 403.
- Подмена actor ID, роли, scope, `granted_by`, `revoked_by` в JSON и заголовках не влияет на principal.
- Неизвестная роль, недопустимая комбинация role/scope, scope `contour` → 400.
- Несуществующая или неактивная учётная запись → 404/409 без раскрытия лишних данных.
- Несуществующая программа или неактивная/непартнёрская организация → 400/404.
- Самоназначение и назначение administrator/applicant через scoped endpoint → отказ.
- Повторное активное назначение → 409.
- Успешное назначение → grant и аудит фиксируются одной транзакцией.
- Ошибка audit insert → rollback grant.
- Отзыв без причины / повторный отзыв / DELETE → отказ.
- Успешный отзыв → audit event и исключение grant из следующего principal.
- MFA отсутствует или не подтверждена → endpoint недоступен.
- Параллельные назначения/отзывы не создают дубли и не нарушают lifecycle.

## 8. Критерии допуска к production

1. MFA для privileged roles реально реализована и enforced на сервере.
2. Двухстороннее согласование назначения независимого проверяющего и администратора реализовано.
3. Все тесты API и PostgreSQL integration tests проходят.
4. Проверены гонки, транзакционные rollback, аудит, CSRF и rate limiting.
5. Security review выполнен отдельно от автора реализации.
6. Backend развёрнут в защищённой российской инфраструктуре с секретами вне репозитория, TLS, резервным копированием и мониторингом.
7. До выполнения этих критериев управление полномочиями остаётся закрытым; GitHub Pages не используется для хранения персональных и служебных данных.

## 9. Принцип внедрения

Не ослаблять текущий fail-closed контроль ради удобства интерфейса. Сначала MFA и независимое согласование, затем scoped-grant API, после этого административный интерфейс. UI не является источником полномочий и не должен иметь прямого доступа к БД.

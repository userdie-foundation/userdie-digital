# MVP: путь заявителя и обработка обращения

**Статус:** проектная спецификация; не означает, что приём обращений включён.  
**Контур:** USERDIE Digital / благотворительный фонд «УСЕРДИЕ».  
**Назначение:** сделать обращение за помощью понятным для заявителя и управляемым для команды фонда.

## 1. Принцип запуска

До отдельного решения фонда публичный сайт и кабинеты остаются информационными демонстрационными экранами. Реальные персональные данные, документы и обращения через них не принимаются.

Переход к рабочему приёму возможен только после одновременного выполнения контрольных условий:

- утверждены правила приёма, рассмотрения, отказа, повторного обращения и обжалования;
- утверждены политика обработки персональных данных, сроки хранения и порядок удаления;
- назначены ответственные за каждую программу и этап;
- развёрнуты API и база данных в контролируемой среде;
- включены аутентификация, серверная авторизация, аудит, резервное копирование и мониторинг;
- пройдены приёмочные, негативные и security-тесты;
- фонд отдельно подтвердил готовность к эксплуатации.

## 2. Путь заявителя

1. **Понять, куда обращаться.** На публичной странице простым языком описаны направления помощи, базовые критерии и ограничения. Если программа закрыта или ещё не утверждена, это видно до начала заполнения.
2. **Узнать, что потребуется.** До сбора данных человек видит цель каждого поля, обязательность, основание запроса и альтернативный способ связи.
3. **Подать обращение.** Рабочая форма собирает только минимально необходимые сведения. Документы запрашиваются позднее, если без них нельзя рассмотреть конкретный вопрос.
4. **Получить подтверждение.** После успешной транзакции заявитель получает номер обращения и дату регистрации. Повторная отправка из-за задержки сети не должна создавать дубликат.
5. **Следить за ходом рассмотрения.** В кабинете показываются понятный статус, дата последнего изменения и безопасно сформулированный следующий шаг.
6. **Ответить на уточнение.** Запрашиваются только конкретные недостающие сведения. Заявителю объясняется, почему они нужны и до какой даты желательно ответить.
7. **Получить результат.** Решение и дальнейшие действия изложены ясным языком. Само наличие обращения не является обещанием предоставления помощи.

## 3. Статусы для человека

Внутренние статусы базы данных не следует без пояснений показывать заявителю. Пользовательское представление должно использовать утверждённый словарь:

| Внутреннее состояние | Текст для заявителя | Что делать |
|---|---|---|
| submitted | Обращение получено | Ожидать проверки |
| in_review | Обращение рассматривается | Дополнительных действий пока не требуется |
| needs_information | Нужны уточнения | Посмотреть запрос и ответить безопасным способом |
| approved | Принято положительное решение | Ознакомиться с условиями и дальнейшими шагами |
| rejected | Помощь по этому обращению не согласована | Прочитать объяснение и доступный порядок повторного обращения |
| withdrawn | Обращение отозвано | При необходимости связаться с фондом по опубликованному каналу |
| completed | Рассмотрение завершено | Сохранить итоговый ответ |

Тексты и юридически значимые основания решения должны быть утверждены фондом. Система не должна автоматически подменять мотивированное решение шаблонным статусом.

## 4. Минимальные данные и конфиденциальность

- Не собирать диагнозы, сведения о здоровье, семейные обстоятельства, паспортные данные и документы «на всякий случай».
- Для каждого поля документировать цель, правовое основание, обязательность, срок хранения и круг доступа.
- Не помещать персональные данные в URL, аналитику, клиентские логи, уведомления на экране блокировки или публичные отчёты.
- Файлы хранить вне публичного каталога сайта; проверять тип, размер и содержимое до предоставления доступа.
- Ссылки на документы должны быть краткоживущими и выдаваться только после серверной проверки прав.
- В тестах использовать синтетические данные; не копировать реальные дела в тестовые среды.
- Не передавать партнёрам сведения по умолчанию: доступ к конкретной записи должен быть отдельно разрешён и журналироваться.

## 5. Роли и границы доступа

| Роль | Минимально необходимый доступ |
|---|---|
| Заявитель | Только собственные обращения и ответы фонда |
| Специалист по делу | Назначенные ему обращения и необходимые задачи |
| Руководитель программы | Обращения только в пределах своей программы |
| Партнёр | Только записи, явно предоставленные этому партнёру |
| Аудитор | Журналы и агрегированная аналитика; без содержания дела по умолчанию |
| Администратор платформы | Настройка системы; административная роль сама по себе не даёт доступа к содержанию дел |

Роль и область доступа определяются сервером из доверенной сессии и базы данных. Клиентские параметры, скрытые поля и переданный браузером идентификатор пользователя не являются доказательством полномочий.

## 6. Требования к интерфейсу и доступности

- Один экран — одна понятная задача; короткие предложения и отсутствие необъяснённых сокращений.
- Видимые подписи у всех полей; ошибки размещаются рядом с полем и объявляются вспомогательным технологиям.
- Полная работа клавиатурой, логичный порядок Tab, заметный фокус и возможность закрыть диалог клавишей Escape.
- Контраст текста и элементов управления не ниже WCAG 2.2 AA; масштабирование текста без потери функций.
- Элементы управления достаточно крупные для пользователей с моторными ограничениями.
- Не использовать только цвет для передачи статуса.
- Не стирать заполненные данные при исправлении ошибки; предупреждать перед необратимым действием.
- Предусмотреть альтернативный канал связи, опубликованный фондом и проверенный до запуска.

## 7. Обязательные приёмочные сценарии

1. Неавторизованный пользователь не получает доступ к частным обращениям.
2. Заявитель не может прочитать обращение другого человека, даже подменив ID в URL.
3. Сотрудник видит только назначенные ему дела; руководитель — только свою программу.
4. Партнёр не видит запись без явного предоставления доступа.
5. Администратор не получает автоматического доступа к содержанию дел.
6. Отозванная роль или завершённая сессия немедленно прекращает соответствующий доступ.
7. Повторный запрос после сетевого тайм-аута не создаёт дубликат обращения.
8. Каждое изменение статуса, назначение и запрос уточнений оставляют неизменяемое событие аудита с актором и временем.
9. Пользователь видит понятное сообщение при временной недоступности сервиса; система не сообщает об успешной отправке, если транзакция не подтверждена.
10. На мобильном устройстве и при использовании клавиатуры можно завершить каждый доступный сценарий без потери контекста.

## 8. Что не входит в первый релиз

- автоматическое решение о предоставлении или отказе в помощи;
- автоматическое ранжирование людей по уязвимости без утверждённой методики и человеческой проверки;
- публичная загрузка документов без авторизации и антивирусной проверки;
- обмен персональными данными с партнёрами без отдельного основания и разрешения;
- обещание сроков или результата помощи, пока фонд не утвердил регламент и ресурсную модель.

## 9. Критерий готовности

MVP считается готовым не по наличию экранов, а когда заявитель может безопасно пройти утверждённый сценарий, команда фонда — обработать обращение по регламенту, а независимая проверка подтверждает разграничение доступа, аудит, доступность и восстановление после сбоя. До этого кабинет остаётся демонстрационным.

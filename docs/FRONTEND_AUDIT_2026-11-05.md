## 3. Замечания и риски

### 3.1. Поддерживаемость CSS

В `website/styles.css` обнаружено большое количество повторяющихся медиаблоков и последовательных переопределений правил навигации и шапки. Это не доказывает наличие визуальной ошибки, но повышает риск конфликтов при дальнейшей разработке и усложняет регрессионную проверку.

**Рекомендация:** провести отдельную консолидацию CSS по компонентам (шапка/навигация, главная секция, карточки, кабинеты, адаптивность), сохраняя текущий визуальный результат. Перед заменой стилей сравнить поведение на контрольных ширинах 390, 680, 900 и 1100 px.

### 3.2. Навигация на мобильных устройствах

В стилях встречаются горизонтальная прокрутка навигации и последующие правила переноса ссылок. По одному исходнику нельзя достоверно определить, как эти переопределения выглядят на реальном устройстве.

**Рекомендация:** визуально проверить шапку на узком мобильном экране и планшете: отсутствие обрезанных пунктов, перекрытия CTA, горизонтального переполнения всей страницы и неудобной прокрутки.

### 3.3. Ссылки на демонстрационные кабинеты

Ссылки на кабинеты и рабочие пространства ведут в каталог `website/prototype/`. Их наличие не является подтверждением действующей авторизации, защищённого хранения данных или реального приёма обращений.

**Рекомендация:** сохранять заметную маркировку демонстрационного режима до появления серверной авторизации, проверок доступа и утверждённых правил обработки данных.

### 3.4. Безопасность и персональные данные

В репозитории уже существует backend-фундамент: Node.js API, PostgreSQL migrations 001–007, хеширование opaque session tokens, scrypt password-verifier primitive, resolver серверного principal и read-only маршруты с проверками scope. Это существенная реализованная инженерная база. При этом login/session issuance, rotation/revocation endpoints, MFA, CSRF-защита, распределённый rate limiting, recovery, write API и production deployment ещё не подтверждены. Документ `SECURITY_READINESS_REVIEW.md` описывает более ранний API draft с placeholder URL; его нельзя трактовать как полное описание текущего backend. До завершения перечисленных контролей нельзя собирать реальные персональные данные заявителей, благополучателей, доноров или сотрудников.

## 4. Следующие инженерные задачи

1. **Проверка ссылок по всему сайту:** пройти все HTML-файлы `website/`, проверить локальные пути, якоря, изображения, документы и навигацию между прототипами.
2. **Регрессионная адаптивность:** проверить главную страницу и ключевые демонстрационные экраны на контрольных размерах 390 / 680 / 900 / 1100 px.
3. **Консолидация CSS:** устранить дублирующие и конфликтующие правила без изменения утверждённой визуальной концепции.
4. **Единый стандарт статусов:** привести карточки модулей к единой терминологии «опубликовано / демонстрация / в разработке / заблокировано до выполнения требований».
5. **Контур безопасности:** до подключения реальных данных реализовать и протестировать серверную аутентификацию, авторизацию на уровне записей, аудит действий и разграничение ролей.
6. **Приёмка публикации:** после изменений в `website/**` дождаться успешного GitHub Actions workflow и отдельно проверить опубликованный URL. Коммит сам по себе не считается публикацией.

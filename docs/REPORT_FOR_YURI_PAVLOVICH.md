# Доклад о состоянии цифровой платформы «Усердие»

**Адресат:** Юрий Павлович  
**Дата:** 19 октября 2026 года  
**Проект:** USERDIE Digital — цифровая инфраструктура Благотворительного фонда «Усердие»  
**Репозиторий:** https://github.com/userdie-foundation/userdie-digital

## 1. Краткое резюме

Проект развивается в правильной для сохранения контроля модели: исходный код и история изменений находятся в GitHub, а домен предполагается подключать через DNS у регистратора REG.RU. Платформу не переносим в сторонний конструктор и не связываем с ним как с единственным местом хранения.

Создан публичный сайт фонда и интерактивный рабочий макет платформы. Последняя проверенная сборка и публикация через GitHub Actions завершилась успешно. При этом текущий интерфейс остаётся демонстрационным: полноценная серверная логика, реальные учётные записи, защищённая база данных и обработка настоящих заявок ещё не введены в эксплуатацию.

## 2. Что уже сделано

- Организован репозиторий проекта и сохранение изменений в Git.
- Подготовлены публичные страницы и навигация между концепцией платформы, кабинетом заявителя, партнёрским пространством и планом реализации.
- Создан интерактивный макет рабочего пространства с разделами «Обзор», «Задачи», «Программы», «Партнёры», «Документы», «Доступы и безопасность».
- В макете реализованы демонстрационные действия с задачами и переключение разделов. Эти действия не сохраняются на сервере и не являются рабочим документооборотом.
- Добавлены документы по архитектуре системы, модели данных, API, инженерным принципам, дорожной карте и восстановлению.
- В GitHub Actions настроена автоматическая проверка внутренних ссылок и публикация сайта на GitHub Pages.

## 4. Что ещё не готово

Следующие возможности нельзя считать запущенными:

- регистрация, вход и восстановление доступа пользователей;
- серверная проверка ролей и разрешений;
- рабочая база данных и резервное копирование с проверенным восстановлением;
- хранение документов в защищённом хранилище;
- приём, регистрация, рассмотрение и отслеживание настоящих заявок;
- журнал аудита реальных действий пользователей;
- интеграции с почтой, уведомлениями и платёжными системами;
- подтверждённая проверка доступности пользовательского домена по HTTPS.

До завершения этих работ в демонстрационный интерфейс нельзя вносить реальные персональные данные, документы заявителей или сведения ограниченного доступа.

## 5. Рекомендуемый план дальнейшей реализации

### Этап 1. Зафиксировать основу
- Проверить публичный домен, DNS и HTTPS отдельно от статуса GitHub Actions.
- Сверить публичные страницы, ссылки и юридически значимые сведения фонда.
- Уточнить, какие роли и процессы нужны для первого рабочего запуска.

### Этап 2. Реализовать серверный контур
- Выбрать совместимый с требованиями фонда способ размещения backend и базы данных, не перенося исходный код из GitHub.
- Создать схему базы данных, миграции и API.
- Реализовать аутентификацию, разграничение доступа и аудит.
- Хранить ключи и пароли только в защищённых настройках окружения, не в репозитории.

### Этап 3. Запустить первый реальный рабочий процесс
- Начать с одного сквозного сценария: заявка → регистрация → назначение ответственного → смена статуса → журнал действий.
- Добавить защищённое хранение приложенных документов и правила доступа.
- Покрыть ключевые операции тестами и проверить отказоустойчивость и восстановление резервной копии.

### Этап 4. Подготовить ограниченный пилот
- Проверить сценарии под разными ролями.
- Провести тестирование безопасности и корректности обработки персональных данных.
- Запускать работу с реальными заявителями только после приёмки и проверки юридических требований.

## 6. Принцип размещения

Рекомендуемая схема сохраняет контроль фонда над проектом:

- **GitHub** — исходный код, история изменений, проверки и автоматическая публикация статических страниц.
- **REG.RU** — управление доменом и DNS.
- **Отдельно выбранная серверная инфраструктура** — backend, база данных и защищённые документы после согласования требований и способа размещения.

GitHub Pages подходит для публичного статического сайта, но не заменяет серверную инфраструктуру для защищённых учётных записей и постоянного хранения заявок. Поэтому серверную часть следует подключать отдельно, сохраняя код и управление изменениями в GitHub.

## 7. Итог

На текущем этапе есть опубликованная публичная оболочка, интерактивный макет рабочего пространства, базовая техническая документация и автоматизированная проверка публикации. Это фундамент проекта, но ещё не полноценная эксплуатационная платформа.

**Ближайший приоритет:** отдельно подтвердить работу домена и HTTPS, затем реализовать минимальный защищённый backend и один полный рабочий процесс заявителя. Переход к реальным данным — только после тестирования доступа, хранения и резервного восстановления.

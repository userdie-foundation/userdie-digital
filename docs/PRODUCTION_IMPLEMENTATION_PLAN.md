# План перехода USERDIE Digital к рабочей платформе

**Статус:** проектный план; это не утверждение, что перечисленные серверные функции уже реализованы.  
**Принцип размещения:** исходный код и история изменений остаются в GitHub; REG.RU обслуживает домен и DNS. Публичный сайт продолжает публиковаться из `website/`. Серверную часть следует развернуть отдельно, не переносить репозиторий в конструктор сайтов.

## Целевое состояние

Платформа должна стать рабочей системой для сотрудников фонда, заявителей и партнёров, а не только публичным сайтом или интерактивным прототипом.

### Основные модули

1. **Публичная часть:** информация о фонде, направления помощи, прозрачность, контакты, актуальные программы.
2. **Кабинет заявителя:** регистрация, создание и отслеживание заявки, безопасная передача документов, уведомления и история изменений.
3. **Рабочее пространство фонда:** очередь заявок, назначение ответственных, статусы, внутренние комментарии, контроль сроков и отчётность.
4. **Кабинет партнёра:** предложения о сотрудничестве, подтверждение участия, согласованные документы и результаты совместных программ.
5. **Администрирование:** пользователи, роли, программы, справочники, настройки и журнал аудита.
6. **Отчётность и прозрачность:** агрегированные показатели и публикации без раскрытия персональных данных.

## Архитектурные границы

- **Frontend:** текущий сайт и интерфейсы в репозитории GitHub.
- **Backend API:** отдельное приложение с версионированным API; публичный сайт не должен напрямую обращаться к базе данных.
- **База данных:** PostgreSQL либо эквивалентная реляционная БД с миграциями, ограничениями целостности и резервным копированием.
- **Файлы:** отдельное приватное объектное хранилище; документы не размещать в публичном каталоге сайта или Git.
- **Идентификация:** серверные сессии или проверенный провайдер аутентификации; обязательная проверка прав на сервере для каждого защищённого действия.
- **Наблюдаемость:** структурированные журналы без секретов и лишних персональных данных, мониторинг ошибок и проверка готовности сервиса.
- **Развёртывание:** отдельные окружения разработки, тестирования и production; секреты только в менеджере секретов/защищённых настройках окружения.

Конкретный поставщик backend-хостинга и БД выбирается после проверки доступности, стоимости, условий хранения данных и возможности независимого экспорта. Не привязывать систему к одному визуальному конструктору.

## Роли и минимальные права

| Роль | Базовые права |
|---|---|
| Заявитель | Создаёт и просматривает только собственные заявки; загружает документы к ним |
| Специалист фонда | Просматривает назначенные заявки и меняет разрешённые статусы |
| Руководитель программы | Управляет заявками и отчётностью своей программы |
| Партнёр | Видит только данные, явно предоставленные ему в рамках сотрудничества |
| Администратор | Управляет учётными записями и конфигурацией; административные действия журналируются |
| Аудитор | Просмотр разрешённых журналов и отчётов без возможности изменять заявки |

Это исходная модель для согласования; доступы должны уточняться с учётом реальных обязанностей фонда.

## Базовые сущности данных

- `users`, `roles`, `user_roles`
- `programs`, `projects`
- `applications`, `application_status_history`, `assignments`
- `documents`, `document_access_events`
- `organizations`, `partnerships`
- `notifications`
- `audit_events`

Для каждой заявки нужны идентификатор, автор, программа, текущий статус, ответственный, даты создания/обновления и история переходов. Статусы меняются только через серверные правила; критические изменения пишутся в аудит.

## Безопасность и защита данных

1. Закрыть доступ к API по умолчанию; проверять авторизацию и объектные права на сервере.
2. Валидировать входные данные на сервере, ограничивать размер и тип загружаемых файлов, сканировать файлы перед доступом к ним.
3. Не хранить пароли в открытом виде, токены, ключи, документы заявителей или персональные данные в Git.
4. Применять HTTPS, защиту от CSRF/XSS/инъекций, ограничение частоты запросов и безопасные cookie.
5. Файлы выдавать только через короткоживущие подписанные ссылки после проверки прав.
6. Определить сроки хранения и удаления данных, согласия, порядок обработки запросов субъектов данных и процедуру реагирования на инциденты до запуска приёма реальных заявок.
7. Резервные копии базы и файлов шифровать и регулярно проверять восстановлением. Наличие плана само по себе не означает, что копии уже настроены.
8. Не использовать реальные данные благополучателей в тестовом окружении.

## Этапы реализации и критерии приёмки

### Этап 0 — Инфраструктурная основа
- Подтвердить работу домена, HTTPS и DNS.
- Проверить GitHub Actions после добавления `website/CNAME`.
- Выделить отдельные окружения и определить владельцев доступа.
- Подготовить схему конфигурации без фиксации секретов в репозитории.

**Приёмка:** публичный сайт доступен по HTTPS на домене; автоматическая публикация и проверка ссылок проходят; инструкция восстановления проверена по шагам.

### Этап 1 — API и база данных
- Создать серверное приложение и версионированные маршруты API.
- Подключить миграции БД, проверку конфигурации и health/readiness endpoints.
- Реализовать тесты схемы данных и основных правил доступа.

**Приёмка:** приложение разворачивается из GitHub по воспроизводимой инструкции; миграции проходят на чистой тестовой БД; секреты не попадают в логи.

### Этап 2 — Вход и права
- Реализовать вход, выход, восстановление доступа и серверную модель ролей.
- Проверить горизонтальное повышение привилегий и доступ к чужим объектам.

**Приёмка:** автоматические тесты подтверждают запрет доступа к чужим заявкам и документам для каждой роли.

### Этап 3 — Заявки и документы
- Реализовать создание заявки, валидацию, жизненный цикл статусов, назначение ответственного и загрузку документов в приватное хранилище.
- Добавить историю действий и уведомления.

**Приёмка:** заявка проходит полный тестовый цикл от подачи до решения; все переходы записаны; файлы недоступны без авторизации.

### Этап 4 — Рабочее пространство и партнёры
- Подключить интерфейс к реальному API вместо браузерных демонстрационных данных.
- Реализовать программы, партнёрские процессы, поиск, фильтры, отчёты и экспорт с проверкой прав.

**Приёмка:** ключевые операции сохраняются в БД, видны после повторного входа и покрыты тестами.

### Этап 5 — Production readiness
- Нагрузочные и security-тесты, мониторинг, резервное копирование и пробное восстановление.
- Проверка доступности с мобильных устройств, доступности интерфейса и документации операторов.
- Ограниченный пилот с тестовыми данными и письменным разрешением ответственного лица.

**Приёмка:** устранены критические уязвимости; восстановление подтверждено тестом; назначены ответственные за поддержку и инциденты.

## Следующие инженерные действия

1. Завершить проверку custom domain и HTTPS, не считать добавление CNAME доказательством корректности DNS.
2. Зафиксировать фактический workflow публикации и критерии его успешности.
3. Подготовить минимальный backend-проект и тестовую среду в этом же репозитории отдельным модулем, не меняя публичную публикацию до проверки.
4. До реальной обработки заявок согласовать правила персональных данных, юридические основания обработки и сроки хранения.
5. Разделять статус каждой функции на **план**, **в разработке**, **проверено в тесте**, **в production**.

## Что не считается готовым

Документация, прототипы, успешная публикация статического сайта и наличие файла домена не означают, что существуют рабочие учётные записи, база заявок, защищённое хранилище, автоматические уведомления или production backend. Эти компоненты должны быть реализованы и отдельно проверены.

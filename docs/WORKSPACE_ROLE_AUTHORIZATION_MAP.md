# USERDIE Digital — связь ролей рабочего пространства с серверными полномочиями

**Статус:** архитектурная спецификация на основе текущей реализации репозитория. Не является утверждением о production-развёртывании или действующих учётных записях.

## 1. Главное правило

Названия ролей в интерфейсе рабочего пространства — это организационные обозначения. Они не являются серверными ролями и сами по себе не дают доступа.

Сервер принимает решения только по активной учётной записи, действующей сессии и полномочиям, загруженным из PostgreSQL. Роль, scope, actor ID и назначение исполнителя, переданные клиентом, не должны считаться доверенными без серверной проверки.

**Нельзя преобразовывать выбор в HTML-селекте в выдачу полномочий.** Назначение реального пользователя, предоставление или отзыв доступа должны выполняться отдельным контролируемым административным процессом.

## 2. Сопоставление понятий

| Понятие рабочего процесса | Серверная модель | Границы |
|---|---|---|
| Постановщик задачи | Фактический actor ID из проверенной сессии; для записей — поле создателя | Не отдельная роль. Нельзя доверять user ID из тела запроса |
| Исполнитель | `case_worker` и точное совпадение `assigned_to` с ID текущего пользователя | Доступ только к назначенной записи; назначение не определяется текстовой должностью |
| Руководитель программы | `program_manager` с grant на конкретный `program_id` | Не глобальный администратор; права не распространяются на другие программы |
| Независимый проверяющий | `independent_approver` с глобальным или программным scope | Не может проверять собственную подачу; право чтения очереди не означает право принять решение через API |
| Администратор платформы | `administrator` global | Администрирование системы; не автоматическое право на независимое согласование |
| Аудитор | `auditor` global | Чтение аудита и разрешённых аналитических представлений; без права изменять первичные записи |
| Партнёр | `partner` с точным scope организации | Доступ только к разрешённым записям своей организации; внутренние материалы проверки партнёру не открываются |
| Заявитель | `applicant` global плюс совпадение applicant ID | Только собственные обращения и разрешённые открытые программы |

## 3. Отображаемые должности и ограничения сопоставления

Текущие варианты интерфейса («Координатор программы», «Специалист по обращениям», «Юрист», «Специалист по оценке активов», «Аналитик», «Специалист по партнёрствам», «Руководитель направления») остаются справочными названиями функциональных ролей.

- «Специалист по обращениям» может соответствовать `case_worker` только после отдельного назначения полномочия конкретной учётной записи и проверки назначения на конкретную запись.
- «Руководитель направления» не означает `administrator`. Для программного контура требуется `program_manager` с точным scope программы.
- «Юрист» не получает автоматически право независимого согласования. Для этого требуется отдельное назначение `independent_approver`, проверка конфликта интересов и запрет самосогласования.
- «Аналитик» не является существующим серверным role code. Доступ к аналитике должен быть read-only и предоставляться отдельным решением; существующее разрешение `analytics:read` ограничено администратором, аудитором и руководителем конкретной программы.
- Для специалиста по оценке активов отдельный серверный role code и модель scope пока не утверждены. Не выдавать ему права администратора, аудитора или независимого согласующего по аналогии названия должности.
- Для координатора программы нужно определить, является ли он постановщиком (атрибут создателя) или руководителем конкретной программы. Не смешивать эти функции.
- Специалист по партнёрствам не получает автоматически доступ к закрытым документам партнёра или внутренним доказательствам. Действуют отдельные правила `partner` и record-level authorization.

## 4. Принцип разделения обязанностей

Для решений с юридическими, финансовыми, оценочными или иными существенными последствиями применяется независимое согласование:

1. Автор/постановщик подаёт материал и фиксируется как actor.
2. Материал получает версию, чтобы проверяющий видел неизменённый комплект.
3. Проверяющий назначается отдельно и не совпадает с автором.
4. Сервер проверяет действующее полномочие и scope проверяющего.
5. Решение и обоснование записываются в отдельную историю событий.
6. Изменение материала после подачи требует новой версии и повторного согласования.
7. Отзыв полномочия прекращает доступ; прошлые события остаются в журнале.

Наличие таблиц и read-only разрешений для очереди согласований не означает, что HTTP-маршрут принятия решения уже реализован. До реализации и тестирования такого маршрута согласование остаётся недоступным через API.

## 5. Области доступа

Существующая схема scoped grants поддерживает `program`, `organization` и `contour`. Наличие типа scope в БД само по себе не означает, что каждый endpoint проверяет его. Каждое новое разрешение должно явно проверять конкретный тип и идентификатор scope в policy и запросе к данным.

Для будущего контура активов требуется отдельно утвердить:
- тип scope (например, конкретный реестр, оценочное задание или объект);
- роли инициатора, оценщика, независимого рецензента и утверждающего;
- ограничения на конфликт интересов;
- доступ к исходным документам и чувствительным финансовым данным;
- отдельные права на просмотр, подготовку заключения, рецензирование и утверждение.

До такого утверждения не использовать `contour` как универсальный пропуск к данным всех трёх контуров.

## 6. Текущие технические ограничения

- В рабочем HTML-макете роли сохраняются локально в браузере и не являются серверными назначениями.
- Серверный resolver получает полномочия из БД по действующей сессии; клиентские поля ролей не являются источником доверия.
- Публичного API для выдачи и отзыва scoped grants нет; миграции предусматривают журналируемый жизненный цикл полномочий.
- Для задач реализован ограниченный маршрут перехода статуса; он не создаёт задачи и не изменяет остальные поля задачи.
- Независимое согласование имеет основу данных и чтения очереди/деталей, но не полный маршрут принятия решения.
- MFA не внедрена и не enforced; привилегированные кабинеты нельзя считать защищёнными MFA.
- Backend не подтверждён как развёрнутый в production; миграции не подтверждены как применённые к production БД.
- Статический сайт GitHub Pages не должен принимать или хранить реальные закрытые данные.

## 7. Этапы реализации

### Этап 1 — утверждение модели
Утвердить перечень ролей, полномочия, контуры и scope, независимость проверяющего, матрицу доступа и ответственных за выдачу/отзыв полномочий.

### Этап 2 — серверные тесты
Для каждого разрешения добавить позитивные и негативные тесты: чужая запись, другой scope, приостановленная учётная запись, отозванный grant, подмена actor ID, попытка самосогласования, неизвестная роль и недоступность БД.

### Этап 3 — управление полномочиями
Разработать закрытый административный процесс выдачи/отзыва grant с двойным контролем для привилегированных ролей, обязательным основанием, сроком действия при необходимости и append-only аудитом. Не открывать публичный endpoint без отдельной модели угроз и приёмки.

### Этап 4 — MFA и ввод в эксплуатацию
Сначала реализовать MFA для привилегированных ролей и проверку сессии, затем провести staging-приёмку, резервное копирование/восстановление, проверку журналов и независимый security review. Production-включение — отдельное управленческое решение.

## 8. Критерий готовности

Ролевая модель считается реализованной только когда сервер проверяет полномочие и scope для каждого защищённого действия, негативные тесты проходят, отзыв полномочия действует немедленно, критические решения аудируются, а развёртывание и эксплуатационные настройки подтверждены отдельно.

**Запрещено считать выбор функциональной роли в интерфейсе доказательством личности, назначения, квалификации или полномочий сотрудника.**

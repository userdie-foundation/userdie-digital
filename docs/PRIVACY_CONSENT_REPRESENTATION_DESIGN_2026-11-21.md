# USERDIE Digital — проектирование согласия через представителя

**Дата:** 21.11.2026  
**Статус:** архитектурное предложение; не реализация и не юридическое заключение.  
**Ветка:** feature/valuation-workspace-api-integration  
**Базовая техническая точка:** migration 021 / privacy consent ledger.  
**Решение по безопасности:** представительский capture остаётся выключенным до отдельной правовой приёмки и реализации.

## 1. Задача и границы

Текущий журнал согласий фиксирует одно и то же лицо как субъекта данных и действующее лицо. Это безопасно для self-service, но не покрывает случаи, когда согласие от имени субъекта даёт представитель.

Новая модель должна различать:
- **субъект данных (data subject)** — физическое лицо, к которому относятся данные;
- **действующее лицо (actor)** — субъект либо представитель, который совершает действие;
- **основание полномочий** — проверяемое юридическое основание, позволяющее этому представителю действовать в конкретном объёме;
- **проверяющий** — уполномоченный сотрудник Фонда, который проверил личность и полномочия до регистрации согласия.

Нельзя принимать идентификатор субъекта из произвольного поля клиентского запроса. Сервер должен сам разрешать субъект через проверенную связь представительства и авторизационный контекст.

## 2. Правовая рамка — не универсальная доверенность

Статья 9 часть 1 152-ФЗ допускает согласие представителя в подтверждаемой форме и возлагает на оператора обязанность проверить полномочия представителя. Часть 4 той же статьи устанавливает дополнительные реквизиты письменного согласия, включая идентификационные сведения представителя и реквизиты документа о полномочиях. Часть 6 предусматривает согласие законного представителя в случае недееспособности субъекта.

Из этого не следует, что любой пользователь, назвавший себя родственником или помощником, может дать согласие за другого человека. Правовой режим зависит от:
- возраста субъекта и применимых норм о дееспособности;
- статуса лица (родитель, усыновитель, опекун, попечитель, представитель по доверенности или иной предусмотренный законом статус);
- объёма полномочий и конкретного действия;
- вида данных и правового основания обработки;
- характера действия: внутреннее согласие, письменное согласие на специальные категории, распространение, использование изображения — самостоятельные юридические действия.

**Обязательное правило:** перед запуском определить матрицу полномочий для каждой категории представителя и типа согласия. Не считать родство само по себе достаточным доказательством полномочий. Не предполагать, что полномочие дать согласие на обработку автоматически охватывает публичное распространение истории/изображения.

## 3. Разрешённые классы представительства — только после правовой матрицы

Предлагаемые технические типы, которые сами по себе не дают полномочий:
- `parent` — родитель/усыновитель;
- `guardian` — опекун;
- `trustee` — попечитель;
- `attorney_in_fact` — представитель по доверенности;
- `other_statutory_representative` — иной представитель, прямо предусмотренный применимым законом.

Сервер не должен разрешать новый тип только потому, что он присутствует в enum. Для каждого типа должны быть утверждены: применимые категории субъектов, допустимые действия, доказательства полномочий, срок действия, случаи прекращения/оспаривания и перечень согласий, которые он вправе давать.

Случаи несовершеннолетних требуют отдельной таблицы возрастных режимов и оценки мнения/воли самого ребёнка в соответствии с применимым законодательством. До такой проверки не включать общий сценарий «родитель согласен — публикация разрешена».

## 4. Предлагаемая модель данных

### 4.1. Реестр полномочий представителя

Отдельная сущность `privacy_representative_authorizations`:
- `id` — случайный внутренний UUID;
- `subject_user_id` — субъект, от имени которого действует представитель;
- `representative_user_id` — проверенная учётная запись представителя;
- `representative_type` — один из утверждённых типов;
- `authority_basis_code` — код правового основания из закрытого справочника;
- `evidence_object_id` — ссылка на закрытое хранилище подтверждения;
- `evidence_sha256` — хэш точного файла/доказательства;
- `verified_by`, `verified_at` — независимая проверка сотрудником;
- `valid_from`, `valid_until` — период действия, если применимо;
- `scope_codes` — утверждённые полномочия (не свободный текст);
- `status` — pending / verified / rejected / expired / revoked;
- `created_at`, `revoked_at`, `revocation_reason_code`.

Документ-основание хранить отдельно в закрытом объектном хранилище с отдельными правами доступа и сроком хранения. Не помещать сканы паспорта, номера документов, адреса и свободный текст в append-only журнал событий. В ledger хранить только ссылку, хэш и минимум атрибутов, необходимых для доказуемости.

### 4.2. Событие согласия

Расширение consent event (или отдельная версия схемы) должно разделять:
- `subject_user_id` — неизменяемый субъект;
- `actor_user_id` — пользователь, совершивший действие;
- `actor_capacity` — self или представитель;
- `representative_authorization_id` — обязательная ссылка для representative;
- `authority_basis_snapshot` — код основания и scope на момент согласия;
- `evidence_ref` — защищённая ссылка на подтверждение проверки;
- `capture_method` — контролируемый метод получения согласия;
- `document_code`, `document_version`, `document_sha256`;
- `choices` — только утверждённые булевы ключи;
- database-owned `occurred_at`.

Текущее ограничение actor = subject не снимать до того, как новая схема и тесты будут готовы. Не допускать nullable actor для представительских событий.

## 5. Серверный процесс выдачи согласия

1. Пользователь проходит обычную аутентификацию как actor.
2. Если actor действует не за себя, сервер находит активную проверенную authorization record; клиент не может передать или подменить subject ID.
3. Проверяются статус полномочий, срок, scope, тип согласия, тип данных и связь с конкретным документом/целью.
4. Для письменного согласия проверяется допустимый метод подписи и полный набор реквизитов; обычная web-сессия не считается письменной подписью.
5. Для специальных категорий отдельный письменный процесс проверяется независимо от обычного personal_data endpoint.
6. Перед сохранением второй сотрудник подтверждает полномочия/документ, если это установлено матрицей риска. Автоматическая проверка файла или OCR не заменяет юридическую оценку.
7. Событие записывается транзакционно с раздельными actor/subject и неизменяемой ссылкой на authorization.
8. Пользователь получает подтверждение с номером записи и точной версией документа; субъекту предоставляется понятный способ проверить и оспорить запись.

## 6. Отзыв и прекращение полномочий

- Субъект может обратиться за прекращением обработки/отозвать собственное согласие через проверенный канал.
- Представитель может действовать только пока его полномочия действуют и только в пределах подтверждённого scope.
- Отзыв/истечение полномочий не удаляет историческое событие согласия; создаётся отдельное событие прекращения полномочий.
- При споре о полномочиях, отзыве доверенности, смене опекуна или конфликте представителей новые действия блокируются до проверки.
- Отзыв полномочий сам по себе не заменяет отзыв ранее данного согласия: правовые последствия ранее совершённого действия квалифицируются отдельно.
- Все запросы субъекта и представителя проверяются на конфликт интересов и безопасность ответа; документы не направляются представителю, если право на их получение не подтверждено.

## 7. Защита данных и минимизация

- Разделить доступ к реестру полномочий и к самим документам-основаниям.
- Сотрудник, проверяющий полномочия, не должен автоматически получать полный доступ ко всем медицинским/социальным материалам субъекта.
- В аудите фиксировать кто, когда, на каком основании и в каком объёме проверил полномочия, но не дублировать паспортные реквизиты в логах.
- Ограничить экспорт, предусмотреть журнал просмотра документов и процедуру уничтожения по сроку хранения.
- Использовать MFA для ролей, имеющих доступ к документам-основаниям.
- Не использовать данные представителя для маркетинга или иных целей без отдельного основания.

## 8. Негативные сценарии и обязательные тесты

1. actor пытается передать чужой subject_user_id без активной authorization — отказ.
2. authorization pending/rejected/expired/revoked — отказ.
3. scope не включает требуемый тип согласия или цель — отказ.
4. actor подменяет представителя или тип полномочий — отказ.
5. документ-основание отсутствует, hash не совпадает или проверяющий не авторизован — отказ.
6. два представителя с конфликтующими полномочиями — блокировка и ручная эскалация.
7. доверенность истекла/отозвана между проверкой и фиксацией согласия — повторная проверка в транзакции.
8. субъект сам отзывает согласие после того, как оно было дано представителем — запрос обрабатывается по обычному законному процессу.
9. попытка использовать обычную сессию вместо письменной подписи для сценария, где закон требует письменную форму — отказ.
10. представитель пытается разрешить публичное распространение, но отдельная матрица полномочий/форма не утверждена — отказ.

## 9. План реализации после утверждения

- **Phase A — legal matrix:** российский юрист утверждает классы представителей, возрастные режимы, полномочия и допустимые типы согласий.
- **Phase B — data model:** отдельная миграция с authorization registry, audit events и разделением actor/subject; текущие ограничения migration 021 сохраняются для legacy self-service.
- **Phase C — service layer:** отдельный representative resolver; никаких subject IDs из тела запроса; проверка scope/expiry/status в транзакции.
- **Phase D — evidence vault:** закрытое хранилище документов-оснований, хэширование, доступ по ролям, retention.
- **Phase E — test & staging:** негативные тесты из раздела 8, конкурентные проверки, аудит прав БД, проверка удаления/отзыва.
- **Phase F — release:** письменная юридическая приёмка и отдельное решение Фонда; только затем отдельное feature flag.

## 10. Текущее решение

**Не реализовывать представительский capture в production на текущем этапе.** Migration 021 и текущий API остаются self-only и fail-closed. Документ является проектом архитектуры для согласования, не подтверждает наличие полномочий конкретного лица и не заменяет проверку документов/закона.

# Операторская процедура: реестр версий согласий

**Статус:** проект внутренней процедуры. Не является разрешением на сбор персональных данных и не заменяет юридическое утверждение документов.

## 1. Назначение и границы

Таблица `privacy_consent_documents` — закрытый реестр точных редакций документов согласия. В реестр вносится только финальная редакция, прошедшая юридическое согласование и утверждённая уполномоченным лицом фонда.

Публичного или пользовательского API для регистрации, изменения, публикации либо отзыва редакций нет. Регистрация выполняется только контролируемой административной процедурой с доступом к БД, журналированием операции и независимой проверкой второго сотрудника. Не выполнять SQL от имени runtime-роли приложения.

До отдельного решения фонда и прохождения release gates:
- `PRIVACY_CONSENT_LEDGER_ENABLED=false`;
- реестр остаётся пустым;
- формы сайта не подключаются к API;
- реальные заявления, документы, сведения о здоровье/инвалидности, данные детей и платёжные реквизиты через этот контур не принимаются.

## 2. Обязательные условия до регистрации

1. Проверить актуальные реквизиты фонда по свежей выписке ЕГРЮЛ и полномочия утверждающего лица.
2. Завершить юридическую редакцию документа для конкретной цели и сценария обработки.
3. Указать самостоятельное правовое основание и конкретную цель обработки; не объединять несовместимые цели одним согласием.
4. Утвердить точные названия и смысл всех переключателей/полей согласия. Набор ключей после публикации неизменяем.
5. Зафиксировать номер редакции, дату утверждения, дату фактической публикации и SHA-256 именно того файла, который увидит субъект.
6. Получить вторую проверку: совпадают ли файл, хэш, версия, цель и ключи выбора.
7. Проверить правомерность места хранения, трансграничных передач, договоров с обработчиками и необходимых уведомлений. Наличие записи в этом реестре само по себе не подтверждает соответствие закону.

## 3. Поля реестра

| Поле | Правило |
|---|---|
| `document_code` | Стабильный машинный код, например `aid_support`; 3–64 символа, латиница/цифры/подчёркивание |
| `document_version` | Формат `YYYY-MM-DD.N`; новая редакция получает новый номер |
| `consent_type` | Только `personal_data`, `dissemination` или `special_category` |
| `purpose_code` | Отдельный код конкретной цели |
| `document_sha256` | SHA-256 точного опубликованного файла, 64 строчных hex-символа |
| `choice_keys` | От 1 до 16 точных ключей интерфейса; после регистрации не меняются |
| `approved_by` | UUID утверждающего лица из `app_users`; полномочия подтверждаются отдельно |
| `approved_at` | Фактическая дата/время утверждения |
| `published_at` | Фактическая дата/время размещения именно этой редакции |
| `revoked_at` | Заполняется один раз при прекращении действия версии |

## 4. Расчёт SHA-256

Вычислять хэш после финального сохранения/экспорта документа. Любое изменение содержимого, включая исправление пунктуации или форматирования в самом файле, требует нового хэша и новой версии.

Linux/macOS:

```bash
sha256sum consent-document.pdf
```

PowerShell:

```powershell
Get-FileHash .\consent-document.pdf -Algorithm SHA256
```

Сверить полученные 64 символа с хэшем, рассчитанным вторым проверяющим на том же файле. Не вычислять хэш для черновика, исходника, который отличается от опубликованного PDF, или файла с персональными данными.

## 5. Контролируемая регистрация

Ниже — шаблон для DBA. Это не команда для запуска без заполнения и двухсторонней проверки. Значения в угловых скобках заменить реальными проверенными значениями; не использовать фиктивные UUID и даты.

```sql
BEGIN;

INSERT INTO privacy_consent_documents (
  document_code,
  document_version,
  consent_type,
  purpose_code,
  document_sha256,
  choice_keys,
  approved_by,
  approved_at,
  published_at
) VALUES (
  '<approved_document_code>',
  '<YYYY-MM-DD.N>',
  '<personal_data|dissemination>',
  '<approved_purpose_code>',
  '<64-character-lowercase-sha256>',
  ARRAY['<exact_choice_key_1>', '<exact_choice_key_2>'],
  '<approved_by_app_users_uuid>',
  '<actual_approval_timestamp_with_timezone>',
  '<actual_publication_timestamp_with_timezone>'
);

SELECT document_code, document_version, consent_type, purpose_code,
       document_sha256, choice_keys, approved_by, approved_at,
       published_at, revoked_at
FROM privacy_consent_documents
WHERE document_code = '<approved_document_code>'
  AND document_version = '<YYYY-MM-DD.N>';

COMMIT;
```

Перед COMMIT проверить, что:
- запись ровно одна;
- хэш и ключи совпадают с утверждённым экземпляром;
- утверждение предшествует публикации;
- публикация не выставлена задним числом;
- код/версия не конфликтуют с другой записью.

Если проверка не пройдена, выполнить ROLLBACK, выяснить причину и повторить процедуру с новой проверкой. Не исправлять уже зарегистрированные поля UPDATE-запросом.

## 6. Специальные категории и распространение

`special_category` намеренно не принимается обычным API: письменный механизм получения и доказательства согласия не реализован. Не регистрировать и не активировать такие документы до отдельного юридического и технического решения.

Согласие на распространение персональных данных (`dissemination`) должно быть самостоятельным документом/волеизъявлением, не объединённым с обычным согласием на обработку. Отдельно проверить применимость ст. 10.1 152-ФЗ и форму такого согласия.

## 7. Отзыв версии

Отзыв не удаляет документ и историю событий. Он однократно устанавливает `revoked_at` на фактическое время прекращения действия. После отзыва запись нельзя повторно активировать или переписать; для новой редакции создаётся новая версия.

Пользовательский отзыв ранее выданного согласия — отдельное событие в `privacy_consent_events`, а не изменение исходного события. Отзыв версии документа в каталоге и отзыв согласия конкретного субъекта — разные операции, их нельзя смешивать.

## 8. Контрольный лист перед включением API

- [ ] Миграция применена только в согласованной среде и проверена PostgreSQL integration suite.
- [ ] Утверждённые документы зарегистрированы с подтверждёнными хэшами.
- [ ] Проверены роли и права DBA/runtime; runtime не может менять каталог версий.
- [ ] Подготовлены политика, уведомления, отдельные согласия и каналы запросов субъектов.
- [ ] Установлены законные цели, сроки хранения, порядок уничтожения и доказательства удаления.
- [ ] Проверены локализация, трансграничные передачи, обработчики и инцидентный процесс.
- [ ] Проверена защищённая авторизация, CSRF, журналирование, резервное копирование и восстановление.
- [ ] Выполнены staging-тесты, проверка доступности и независимая юридическая приёмка.
- [ ] Отдельным письменным решением разрешено включение feature flag.

**Ни один пункт этого документа не означает, что миграция уже применена к рабочей БД, документы утверждены, уведомления поданы или сбор реальных данных разрешён.**


## 9. Дополнительные ограничения целостности БД и эксплуатационных ролей

Migration 021 содержит DB-level проверки цепочки согласий. Перед приёмкой новой версии миграции integration suite должен подтвердить:
- действующее лицо `authenticated_session` совпадает с субъектом;
- grant ссылается на существующую, утверждённую, опубликованную и неотозванную версию;
- `special_category` не принимается обычным session-механизмом;
- ключи выбора совпадают с `choice_keys`, все значения boolean, а событие grant содержит хотя бы один положительный выбор;
- новый grant не создаётся поверх последнего активного grant;
- withdrawal ссылается на последнее активное grant-событие того же субъекта и документа; один grant нельзя отозвать повторно;
- каталог версий и журнал событий не очищаются через `TRUNCATE`.

**Минимальная матрица прав runtime-роли для этого контура:** `privacy_consent_documents` — только `SELECT`; `privacy_consent_events` — `SELECT, INSERT`; `audit_events` — `INSERT`; `app_users` — только чтение тех полей, которые нужны для проверки субъекта и авторизации. Не выдавать runtime-роли `UPDATE` на `app_users` или каталог документов, а также `UPDATE/DELETE/TRUNCATE` на журнал событий. Проверить эффективные и унаследованные права, включая членство в групповых ролях: точечный `REVOKE` не отменяет права, полученные через другую роль. Регистрация и отзыв версии документа выполняются отдельной DBA-ролью.

Для сериализации событий по субъекту API и DB-триггер используют транзакционные advisory locks. Для синхронизации выдачи/отзыва версии отдельный advisory lock берётся триггером каталога и триггером события. Это позволяет не давать приложению права блокировки строк через `SELECT FOR UPDATE/SHARE`, которые потребовали бы дополнительных UPDATE-привилегий. DBA-процедура отзыва версии должна выполнять обычный `UPDATE revoked_at` в одной транзакции; триггер сам синхронизирует её с выдачей согласий.
Эти триггеры не защищают от владельца БД или superuser. Для staging/production DBA обязан создать отдельную runtime-role с минимальными правами. Runtime-role не должна владеть схемой, таблицами или функциями и не должна иметь `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, право отключать триггеры или менять привилегии. Регистрация/отзыв версии документа выполняется отдельной DBA-процедурой с двумя проверяющими и независимой сверкой SHA-256.

Текущий API поддерживает только согласие самого аутентифицированного пользователя. Законные представители, письменные согласия на специальные категории, дополнительные электронные подписи/доказательства предъявления текста и сроки хранения/удаления требуют отдельного проектирования и юридического согласования. Не использовать этот endpoint для этих сценариев.

**Проверка миграции:** PostgreSQL integration suite может быть пропущен в CI, если `PG_INTEGRATION_URL` не задан. Перед признанием миграции принятой нужно проверить итог конкретного CI job и убедиться, что интеграционный тест не имеет статуса skipped.

## 10. Контроль каталога полей

При регистрации версии документа база проверяет, что `choice_keys` содержит только уникальные ключи допустимого формата. Дублирующиеся или некорректные ключи отклоняются триггером до сохранения документа. Это дополнение не заменяет независимую проверку человеком полного текста документа и SHA-256.

## 11. Раздельные потоки согласий

Обычный session endpoint принимает только тип `personal_data`. Типы `special_category` и `dissemination` отклоняются и на уровне API, и на уровне PostgreSQL. Для специальных категорий требуется отдельно спроектированный письменный механизм, если согласие является правовым основанием. Для распространения требуется отдельная форма с выбором категорий/условий по ст. 10.1 152-ФЗ и отдельное юридическое согласование. Нельзя регистрировать эти типы с целью обхода ограничений стандартного endpoint.


## 12. Дополнительные release gates: распространение, SLA и двойная проверка

### 12.1. Согласие на распространение — отдельный поток

- Не регистрировать документ типа dissemination в обычном каталоге, пока не утверждены отдельная форма, перечни полей по категориям, URL ресурсов, цель, срок, ограничения и условия передачи.
- Для каждой выданной версии фиксировать отдельный consent artifact, его SHA-256, субъект, контактный способ, версию, поля, выбранные ограничения, каналы/URL, дату и время получения.
- В пределах трёх рабочих дней с момента получения согласия публиковать информацию об условиях обработки и запретах/условиях; сохранять URL публикации и доказательство даты.
- Требование по ч. 12 ст. 10.1 прекращает действие согласия с момента поступления. Немедленно остановить управляемое распространение и запустить уведомление обработчиков/партнёров. Требование по ч. 14 имеет отдельный срок до трёх рабочих дней.
- Не трактовать обычный withdrawal в privacy_consent_events как достаточную остановку публичных публикаций: нужен отдельный реестр публикаций и workflow прекращения доступа.

### 12.2. Контроль сроков субъектных запросов

Использовать матрицу раздела 15 LEGAL_INTERNAL_CONTROLS: 10 рабочих дней + возможное мотивированное продление до 5 рабочих дней для ответа/отказа; 7 рабочих дней для уточнения/уничтожения по ст. 20 ч. 3; 3/10 рабочих дней для неправомерной обработки; 30 календарных дней для достижения цели/отзыва, когда применимо; 10 + 5 рабочих дней для требования о прекращении обработки; до 6 месяцев только при невозможности уничтожения в основной срок и с блокированием. В системе хранить вид события и отдельную контрольную дату, а не один общий SLA.

### 12.3. Независимая проверка версии документа

Каталог должен хранить доказательство независимого контроля: approved_by, approved_at, verified_by, verified_at, approval_record_ref, artifact_sha256 и проверенный перечень choice_keys. Автор/утверждающий не может одновременно выступать единственным независимым проверяющим. Если схема БД пока не имеет этих полей, не имитировать их значениями approved_by; использовать отдельный неизменяемый audit event или отдельную таблицу утверждений в последующей миграции.

### 12.4. Текущий технический предел

В настоящей версии не реализованы dissemination capture, публикационный реестр, отдельная остановка публичных публикаций и представительский capture. Это не исправляется включением feature flag. До отдельной реализации и юридической приёмки все такие сценарии остаются вне API и вне production.

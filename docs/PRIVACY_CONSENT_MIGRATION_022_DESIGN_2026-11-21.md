# USERDIE Digital — проект миграции 022: проверка версии согласия и полномочия представителя

**Дата:** 21.11.2026  
**Статус:** техническая спецификация для review; SQL migration не создана и не применялась.  
**Ветка:** `feature/valuation-workspace-api-integration`  
**Исходная схема:** `backend/migrations/021_privacy_consent_ledger.sql`  
**Решение:** сохранить self-only контур migration 021; не включать представительский capture и не менять production.

## 1. Цель и границы

Подготовить следующий изолированный слой данных для двух ещё не реализованных контрольных функций:

1. независимое подтверждение точной версии согласия (файл, SHA-256, перечень choice keys, утверждение);
2. реестр проверенных полномочий представителя, не содержащий копий паспортов и иных избыточных персональных реквизитов.

Этот документ — проект архитектуры. Он не является SQL-миграцией, не создаёт таблиц, не изменяет API, feature flags, права БД или production. Представительское согласие, письменные согласия на специальные категории и согласие на распространение остаются вне действующего API.

## 2. Факты исходной схемы 021

Проверено по текущей ветке:

- `privacy_consent_documents` — версионный реестр; `approved_by`, `approved_at`, `published_at`, `document_sha256`, `choice_keys`; версия неизменяема, кроме однократного заполнения `revoked_at`.
- `privacy_consent_events` — append-only события grant/withdrawal.
- DB trigger `enforce_privacy_consent_event_integrity()` требует `actor_user_id = subject_user_id`, `capture_method = authenticated_session`; запрещает обычный grant для `special_category` и `dissemination`.
- Текущий HTTP endpoint принимает только `personal_data`; субъект определяется из аутентифицированного principal, а не из тела запроса.
- PostgreSQL integration suite последовательно применяет миграции 001–021 в изолированной схеме. Тест пропускается, если `PG_INTEGRATION_URL` не задан.
- Migration runner требует явного `MIGRATIONS_ALLOW_APPLY=true` и отдельного `MIGRATIONS_DATABASE_URL`.

Эти ограничения считаются действующим security boundary. Проект 022 не должен ослаблять их побочно.

## 3. Проектируемая модель независимой проверки документа

### 3.1. Отдельная таблица доказательства проверки

Предлагаемое имя: `privacy_consent_document_verifications`.

Предлагаемые поля:

| Поле | Назначение |
|---|---|
| `id` | UUID |
| `document_id` | FK на `privacy_consent_documents(id)`, ON DELETE RESTRICT, UNIQUE |
| `author_user_id` | автор текста/артефакта |
| `approver_user_id` | лицо, утвердившее документ; должно совпадать с `privacy_consent_documents.approved_by` |
| `verifier_user_id` | независимый проверяющий |
| `artifact_sha256` | хэш проверенного финального артефакта |
| `choice_keys_snapshot` | точный набор ключей на момент проверки |
| `approval_record_ref` | ссылка/идентификатор записи об утверждении без вложения документа |
| `verified_at` | время проверки, устанавливаемое БД |
| `created_at` | время создания записи, устанавливаемое БД |

Инварианты:

- одна verification-запись на одну версию документа;
- `approver_user_id = privacy_consent_documents.approved_by`;
- `artifact_sha256 = document_sha256`;
- `choice_keys_snapshot` в точности совпадает с `choice_keys` документа (сравнение как множества с запретом дубликатов);
- `verifier_user_id` не равен `author_user_id` и не равен `approver_user_id`;
- автор и утверждающий могут совпадать только если это отдельно допускает утверждённая политика; независимый проверяющий в любом случае отдельное лицо;
- `verified_at` не может предшествовать `approved_at`; публикация не может считаться прошедшей gate до проверки;
- запись неизменяема после вставки; UPDATE/DELETE/TRUNCATE запрещены триггером;
- запись не содержит текста согласия, паспортных реквизитов или содержимого подтверждающих документов.

### 3.2. Gate перед использованием версии

До внедрения требуется выбрать и формально проверить один из вариантов:

**Вариант A — обязательная проверка для всех новых версий.** DB trigger на вставку consent event требует наличие корректной verification-записи. Для ранее зарегистрированных версий нужен контролируемый backfill с реальным вторым проверяющим; нельзя автоматически подставлять `approved_by` в `verifier_user_id`.

**Вариант B — поэтапный ввод.** Добавить явное состояние/политику допуска версии, где legacy-версии остаются заблокированными до верификации, а новые версии обязаны иметь verification-запись. Состояние должно быть серверно- и DB-enforced, а не флагом интерфейса.

Предпочтителен вариант A, если перед применением подтверждено, что каталог пуст либо для каждой существующей версии подготовлены реальные независимые доказательства. Если это условие не подтверждено, миграцию не применять до инвентаризации и backfill-плана.

Проверка должна блокировать выдачу согласия на неверифицированную версию на уровне БД, а не только в HTTP handler. Сама запись verification не должна автоматически активировать документ или заменять правовое утверждение.

## 4. Проектируемая модель полномочий представителя

### 4.1. Неизменяемая запись основания

Предлагаемое имя: `privacy_representative_authorizations`.

Предлагаемые поля:

- `id` UUID;
- `subject_user_id`, `representative_user_id` — FK на `app_users(id)`, ON DELETE RESTRICT; значения различны;
- `representative_type` — закрытый код из юридически утверждённого справочника;
- `authority_basis_code` — закрытый код основания, не свободный текст;
- `evidence_object_ref` — opaque ID защищённого хранилища;
- `evidence_sha256` — SHA-256 подтверждающего файла;
- `scope_codes` — непустой набор закрытых кодов полномочий;
- `valid_from`, `valid_until` — период действия; `valid_until` может быть NULL только если это допустимо для соответствующего основания;
- `registered_by`, `registered_at` — кто и когда внёс запись;
- `verified_by`, `verified_at` — отдельный проверяющий, если конкретный статус требует проверки.

В основной таблице не хранить ФИО, адреса, паспортные данные, диагнозы, сканы и произвольное описание семейной/социальной ситуации. Идентификация пользователя осуществляется через существующий `app_users`; доказательства хранятся в закрытом хранилище с отдельной политикой доступа и retention.

### 4.2. История статусов — append-only

Предлагаемое имя: `privacy_representative_authorization_events`.

Поля: UUID, `authorization_id`, `event_type` (закрытый набор `registered`, `verified`, `rejected`, `revoked`), `actor_user_id`, `reason_code`, `occurred_at` (database-owned), `metadata` только с минимальными не-PHI/non-document данными.

События append-only; UPDATE/DELETE/TRUNCATE запрещены. Текущее состояние вычисляется по последнему допустимому событию и сроку действия, а не из клиентского параметра. Переходы статусов должны быть проверены триггером под транзакционной блокировкой authorization ID. Запрещены переходы из `rejected`/`revoked` обратно в `verified`; для нового основания создаётся новая запись.

Нужно отдельно определить, является ли `registered_by` сотрудником Фонда или доверенным процессом, какие роли могут подтвердить полномочия и какие роли могут отозвать их. Наличие enum само по себе не даёт полномочий.

### 4.3. Серверное разрешение субъекта

Будущий сервис обязан:

1. аутентифицировать actor;
2. при self-service использовать существующий путь 021 без изменений;
3. при представительском действии сам найти запись полномочий по actor, проверить последнее событие статуса, срок действия и требуемые scope/цель/тип согласия;
4. получить subject из этой записи на сервере; игнорировать любые переданные клиентом subject IDs;
5. повторить проверку статуса и срока внутри транзакции непосредственно перед записью события;
6. записать ссылку на authorization и snapshot минимально необходимых полномочий;
7. отказать fail-closed при отсутствии записи, споре, неоднозначности, истечении срока, несовпадении scope или недоступности evidence store.

**Migration 022 не должна изменять функцию `enforce_privacy_consent_event_integrity()` и не должна разрешать actor != subject в таблице `privacy_consent_events`.** Для будущего представительского consent capture потребуется отдельное проектирование схемы события/цепочки и отдельная миграция после legal sign-off. Это не должно ломать или переинтерпретировать self-only историю 021.

## 5. Юридические блокирующие решения

До создания исполняемого SQL Фонд и российский юрист должны утвердить:

- матрицу «тип представителя × возраст/дееспособность субъекта × тип действия»;
- перечень документов, подтверждающих каждый вид полномочий;
- допустимые scope-коды и их связь с целями обработки;
- порядок учёта мнения/воли несовершеннолетнего, когда применимо;
- возможность и форму письменного согласия для соответствующего сценария;
- отдельные правила для специальных категорий, распространения и изображения;
- срок хранения evidence, основания доступа и уничтожения;
- роли и разделение обязанностей author / approver / verifier / authority reviewer.

Нельзя считать родство достаточным доказательством полномочий. Нельзя выводить разрешение на публикацию фото/истории из разрешения на внутреннюю обработку данных.

## 6. Требования к миграции и безопасности

Когда будет разрешено подготовить SQL, миграция должна:

- иметь номер 022 и быть forward-only; не переписывать 021;
- использовать транзакцию `BEGIN/COMMIT`;
- применять FK `ON DELETE RESTRICT`, явные CHECK/UNIQUE и индексы под фактические resolver-запросы;
- задавать database-owned timestamps;
- защищать append-only таблицы от UPDATE/DELETE/TRUNCATE;
- не выдавать runtime-role права владения схемой, изменения функций/триггеров, DDL или управления ролями;
- выдавать runtime только необходимые SELECT/INSERT; DBA registration и review — отдельным least-privilege процессом;
- не считать advisory lock заменой проверок полномочий;
- не включать RLS, пока не будет согласована совместимая модель текущего backend и ролей; отсутствие RLS не должно маскироваться фиктивным заявлением о его наличии;
- не содержать seed-записей, фиктивных пользователей, примеров паспортов или автоматического backfill с подставными reviewer IDs.

Миграция должна быть идемпотентно обнаруживаемой migration runner как новая версия, но не должна запускаться в рамках этой задачи.

## 7. Обязательные тесты до принятия SQL

### Document verification
- mismatch SHA-256 / choice keys / approver — отказ;
- verifier = author или approver — отказ;
- повторная verification-запись — отказ;
- UPDATE/DELETE/TRUNCATE — отказ;
- проверка документа до/после approval и publication;
- grant на неверифицированную версию — отказ на уровне БД;
- проверка backfill-поведения для непустого каталога.

### Representative authorization
- actor = subject не создаёт представительскую запись;
- actor не может указать чужой subject в request body;
- pending/rejected/revoked/expired authorization — отказ;
- неверный scope/цель/тип согласия — отказ;
- subject и representative не могут совпадать;
- отсутствующий или неверный evidence hash — отказ;
- проверяющий не имеет требуемой роли — отказ;
- истечение/отзыв между предварительной проверкой и insert — отказ в транзакции;
- повторное/недопустимое событие статуса — отказ;
- конкурирующие проверки/отзывы сериализуются;
- документы-основания не попадают в API response, обычные логи и audit metadata.

### Regression
- все существующие migration 001–021 и self-only consent tests проходят без изменения семантики;
- actor=subject для обычного endpoint остаётся обязательным;
- special_category и dissemination по-прежнему fail-closed;
- публичный endpoint и feature flag остаются выключенными;
- integration test реально выполняется с PostgreSQL, а не отмечен skipped.

## 8. План реализации после согласования

1. Зафиксировать юридическую матрицу и закрытые справочники.

3. Подготовить SQL 022 отдельным изменением и ревьюировать его независимо.
4. Добавить unit и PostgreSQL integration tests; обеспечить запуск с выделенным PostgreSQL 16.
5. Провести аудит effective grants, owner, trigger/function privileges и migration runner.

7. Провести legal/security acceptance; отдельно принять решение Фонда о будущей реализации endpoint.
8. Не включать feature flag и не применять в production без отдельного письменного разрешения.

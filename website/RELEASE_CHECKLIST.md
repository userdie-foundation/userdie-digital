# Чек-лист релиза сайта «Усердие»

Этот список фиксирует техническую проверку перед объявлением релиза. Наличие файлов в репозитории само по себе **не означает**, что сайт опубликован или что релиз прошёл проверку.

## 1. Изменения в репозитории

- [ ] Проверить diff и убедиться, что в коммитах только согласованные изменения.
- [ ] Проверить ссылки главной страницы на концепцию партнёрского пространства и демонстрационный кабинет заявителя.
- [ ] Проверить переход с карты платформы на концепцию партнёрского пространства и обратно.
- [ ] Проверить относительные пути CSS и навигационные ссылки на главной, карте платформы, кабинете заявителя, партнёрском пространстве и странице 404.
- [ ] Проверить, что `website/404.html` находится в публикуемом каталоге.
- [ ] Проверить HTML на ошибки разметки и корректное отображение кириллицы.

## 2. Интерфейс и доступность

- [ ] Открыть главную страницу на широком экране и на мобильной ширине.
- [ ] Проверить навигацию, кнопки, якоря и отсутствие ссылок на неверные адреса.
- [ ] С карты платформы открыть модуль «Управление программами» и убедиться, что переход ведёт в рабочее демо команды.
- [ ] В рабочем пространстве проверить переходы между обзором, задачами, программами, партнёрами, документами и доступами.
- [ ] В демо задач проверить поиск, фильтр «Активные / Выполненные», добавление задачи и смену статуса; после перезагрузки убедиться, что демо-изменения не выдаются за серверное сохранение.
- [ ] На мобильной ширине проверить горизонтальную навигацию модулей и доступность кнопок без переполнения.
- [ ] Проверить клавиатурный фокус, ссылку «Перейти к содержанию» и читаемость текста.
- [ ] Убедиться, что демонстрационный кабинет явно обозначен как нерабочий макет и не обещает отправку обращений.
- [ ] Проверить страницу 404 и переходы с неё на главную, карту платформы и демонстрационный кабинет.

## 3. Публикация через GitHub Pages

- [ ] Убедиться, что коммиты находятся в ветке `main`.
- [ ] Проверить запуск workflow **Deploy public website** после последнего коммита.
- [ ] Убедиться, что этапы build/upload/deploy завершились успешно.
- [ ] Взять фактический URL из результата GitHub Pages workflow / настройки Pages; не угадывать домен.
- [ ] Открыть фактический публичный URL в браузере и проверить главную страницу.
- [ ] Проверить переходы на `prototype/platform.html` и `prototype/applicant-cabinet.html`.
- [ ] Проверить фактический URL отсутствующей страницы и убедиться, что сервер отдаёт пользовательскую страницу 404.
- [ ] Проверить HTTPS и отсутствие ошибок загрузки CSS в браузере.

## 4. Граница релиза

- [ ] Подтвердить, что опубликованы только статические страницы и что формы/кабинеты не подключены к рабочим данным.
- [ ] Зафиксировать дату, URL, commit SHA и результат проверки Pages.
- [ ] Отдельно согласовать домен, контакты, реквизиты, юридические документы и реальные программы до их публикации.

## Критерий готовности

Релиз можно считать проверенным только после успешного workflow и ручной проверки публичного URL и ключевых переходов. Если запуск workflow или публичный URL недоступны для проверки, статус остаётся **«изменения внесены; публикация не подтверждена»**.

# Чек-лист релиза сайта «Усердие»

Этот список фиксирует техническую проверку перед объявлением релиза. Наличие файлов в репозитории само по себе **не означает**, что сайт опубликован или что релиз прошёл проверку.

## 1. Изменения в репозитории

- [ ] Проверить diff и убедиться, что в коммитах только согласованные изменения.
- [ ] Проверить ссылки главной страницы на концепцию партнёрского пространства и демонстрационный кабинет заявителя.
- [ ] Проверить переход с карты платформы на концепцию партнёрского пространства и обратно.
- [ ] Проверить относительные пути CSS и навигационные ссылки на главной, карте платформы, кабинете заявителя, партнёрском пространстве и странице 404.
- [ ] Проверить, что `website/404.html` находится в публикуемом каталоге.
- [ ] Проверить HTML на ошибки разметки и корректное отображение кириллицы.

## 2. Интерфейс и доступность

- [ ] Открыть главную страницу на широком экране и на мобильной ширине.
- [ ] Проверить навигацию, кнопки, якоря и отсутствие ссылок на неверные адреса.
- [ ] С карты платформы открыть модуль «Управление программами» и убедиться, что переход ведёт в рабочее демо команды.
- [ ] В рабочем пространстве проверить переходы между обзором, задачами, программами, партнёрами, документами и доступами.
- [ ] В демо задач проверить поиск, фильтр «Активные / Выполненные», добавление задачи и смену статуса; после перезагрузки убедиться, что демо-изменения не выдаются за серверное сохранение.
- [ ] В рабочем пространстве проверить локальное сохранение демо-задач: добавить задачу, изменить статус, перезагрузить страницу и убедиться, что состояние восстановилось в том же браузере.
- [ ] Убедиться, что интерфейс явно сообщает: локальное сохранение не является серверным, не обеспечивает синхронизацию между устройствами и не предназначено для реальных обращений или персональных данных.
- [ ] Проверить сценарий недоступного `localStorage`: интерфейс не должен падать или заявлять, что данные сохранены; должно появляться понятное предупреждение.
- [ ] На мобильной ширине проверить горизонтальную навигацию модулей и доступность кнопок без переполнения.
- [ ] Проверить клавиатурный фокус, ссылку «Перейти к содержанию» и читаемость текста.
- [ ] Убедиться, что демонстрационный кабинет явно обозначен как нерабочий макет и не обещает отправку обращений.
- [ ] Проверить страницу 404 и переходы с неё на главную, карту платформы и демонстрационный кабинет.

## 3. Публикация через GitHub Pages

- [ ] Убедиться, что коммиты находятся в ветке `main`.
- [ ] Проверить запуск workflow **Deploy public website** после последнего коммита.
- [ ] Убедиться, что этапы build/upload/deploy завершились успешно.
- [ ] Взять фактический URL из результата GitHub Pages workflow / настройки Pages; не угадывать домен.
- [ ] Открыть фактический публичный URL в браузере и проверить главную страницу.
- [ ] Проверить переходы на `prototype/platform.html` и `prototype/applicant-cabinet.html`.
- [ ] Проверить фактический URL отсутствующей страницы и убедиться, что сервер отдаёт пользовательскую страницу 404.
- [ ] Проверить HTTPS и отсутствие ошибок загрузки CSS в браузере.

## 4. Граница релиза

- [ ] Подтвердить, что опубликованы только статические страницы и что формы/кабинеты не подключены к рабочим данным.
- [ ] Зафиксировать дату, URL, commit SHA и результат проверки Pages.
- [ ] Отдельно согласовать домен, контакты, реквизиты, юридические документы и реальные программы до их публикации.

## Критерий готовности

Релиз можно считать проверенным только после успешного workflow и ручной проверки публичного URL и ключевых переходов. Если запуск workflow или публичный URL недоступны для проверки, статус остаётся **«изменения внесены; публикация не подтверждена»**.

## 5. Серверная готовность и защита данных

- [ ] До включения реальных обращений реализовать и независимо проверить аутентификацию, управление сессиями, выход из системы и отзыв сессий.
- [ ] Проверить разграничение доступа на уровне каждой записи: заявитель видит только собственное обращение; сотрудники — только записи в пределах назначенных полномочий; аудиторы — только разрешённые данные.
- [ ] Реализовать проверку входных данных, ограничения размера запросов, безопасную обработку ошибок и защиту от перебора/злоупотребления.
- [ ] Определить сроки хранения, основания обработки, права доступа, порядок удаления/выгрузки и процедуру реагирования на инциденты до загрузки персональных данных.
- [ ] Проверить аудит чувствительных операций без записи паролей, токенов, содержимого документов и лишних персональных данных в журналы.
- [ ] Проверить резервное копирование и восстановление на тестовом окружении; отдельно зафиксировать RPO/RTO и владельца процедуры.
- [ ] Выполнить тесты безопасности и приёмочные тесты на тестовых данных; не использовать реальные данные благополучателей до письменного допуска ответственных.
- [ ] Подтвердить конфигурацию продакшена, HTTPS, секретов и доступа к базе данных; миграции должны быть проверены и применены контролируемо, а не только находиться в репозитории.
- [ ] Проверить API /api/v1/applications: пока аутентификация и построчный контроль доступа не реализованы, модуль должен оставаться закрытым и не читать/изменять записи.

**Текущая граница:** серверный обработчик намеренно возвращает 503 для /api/v1/applications, а методы записи не разрешены. Миграция 003_auth_sessions.sql создаёт только основу таблицы сессий и сама по себе не включает вход в систему. Это защитное поведение нельзя снимать, пока перечисленные проверки не пройдены.

## 7. Поисковая индексация — Яндекс и Google

Цель: подготовить публичный сайт фонда к корректному обнаружению и индексации в Яндекс Поиске и Google Поиске. Добавление сайта в панели вебмастеров не гарантирует сроки или позиции индексации.

- [ ] Утвердить единственный основной публичный адрес сайта и проверить HTTPS/редиректы www и без www.
- [ ] Подготовить `robots.txt` без блокировки публичных страниц и указать в нём адрес актуальной XML-карты сайта.
- [ ] Создать и проверить `sitemap.xml`: только канонические публичные URL со статусом 200; исключить 404, демонстрационные технические/служебные страницы и закрытые разделы.
- [ ] Проверить title, description, canonical и Open Graph на главной и ключевых публичных страницах; не допускать дублирующих или противоречивых canonical.
- [ ] Проверить, что публичные страницы доступны для роботов и не закрыты случайными `noindex` или правилами robots.
- [ ] Подготовить подтверждение владения доменом через DNS TXT; не менять MX и настройки почты фонда.
- [ ] Добавить сайт в Яндекс Вебмастер, подтвердить права, отправить sitemap.xml и проверить диагностику обхода/индексации.
- [ ] Добавить домен в Google Search Console, подтвердить права, отправить sitemap.xml и проверить отчёты индексирования и доступность URL.
- [ ] Проверить вручную главную страницу и ключевые публичные страницы через инструменты проверки URL обеих систем.
- [ ] Зафиксировать дату подтверждения домена, отправки sitemap и первые результаты обхода. Не обещать появление в выдаче к дате релиза.

**Ограничение:** поисковые системы самостоятельно определяют сроки обхода, индексирования и ранжирования. Подключение Яндекс Вебмастера и Google Search Console — настройка мониторинга и отправка карты сайта, а не гарантия позиции или немедленного появления страниц в поиске.

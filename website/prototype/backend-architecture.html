Проект архитектуры серверного контура для обращений, программ и аналитики. Документ фиксирует границы доверия, API-контракт, модель полномочий, аудит и безопасный порядок пилотного запуска. Он не означает, что сервер, база данных или API уже созданы.

Статус: проектная спецификация для технического и правового согласования. Сейчас сайт USERDIE DIGITAL остаётся статическим публичным интерфейсом. Здесь нет действующей базы обращений, серверной авторизации, защищённого API или интеграции с реальными данными. Не вводить персональные данные и документы в демонстрационные формы. До выбора и утверждения инфраструктуры запрещены production-подключения.

01. Целевая архитектура

Разделить публичный сайт, внутреннее рабочее приложение, защищённый API и аналитическую витрину. Публичный GitHub Pages не должен выступать хранилищем секретов или персональных данных.

  • Клиентский интерфейс: кабинет сотрудников с обязательной серверной проверкой каждого запроса.
  • API gateway: TLS, проверка токена, rate limiting, схемы запросов, correlation ID.
  • Сервис дел: первичная запись, назначения, статусы и сроки.
  • Сервис программ: справочники, владельцы, связи с делами.
  • Audit service: append-only события и защищённый экспорт журнала.
  • Analytics pipeline: минимизация → псевдонимизация → агрегирование → витрина.

05. Обязательные контроли безопасности

  • SSO/OIDC или другой утверждённый провайдер идентификации; MFA для привилегированных ролей.
  • Короткоживущие access tokens, безопасная ротация refresh tokens, отзыв сессий.
  • Проверка полномочий на сервере для каждого объекта и действия; защита от IDOR.
  • Шифрование при передаче и хранении; ключи вне репозитория и frontend.
  • Rate limiting, защита от перебора, CSRF/CORS политика, валидация входных данных.
  • Резервное копирование, проверка восстановления, мониторинг аномалий и план реагирования.
  • Секреты, персональные данные и production-логи не попадают в GitHub.

06. Тестовый контур

Пилот запускается отдельно от публичного сайта и production-систем.

  • Отдельная тестовая БД и отдельные credentials.
  • Только синтетические записи, созданные для тестов; запрещено копировать реальные обращения.
  • Набор тестов: RBAC, объектная изоляция, аудит, валидация, rate limits, экспорт, удаление/retention.
  • Нагрузочные и security-тесты на согласованной тестовой среде.
  • Приёмка: владелец процесса, ответственный за безопасность, юрист/специалист по данным, руководитель фонда.

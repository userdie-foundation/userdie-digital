USERDIE DIGITAL · SECURITY QA

Проверка полномочий.
Ни одного лишнего доступа.

Набор обязательных сценариев для проверки будущей серверной системы. Каждый сценарий должен завершаться воспроизводимым результатом, записью аудита и подтверждением отсутствия обходного пути.

План тестирования Не является отчётом о пройденных тестах

01 / МЕТОДИКА

Тестируем не только успех, но и отказ.

Критические проверки выполняются для каждого endpoint и каждой роли, а не только на уровне скрытия кнопок в интерфейсе.

POSITIVE TESTING

Разрешённое действие

Пользователь с действующим назначением выполняет только ту операцию, которая предусмотрена его ролью и областью доступа.

NEGATIVE TESTING

Запрещённое действие

Пользователь не получает данные и не выполняет команду через прямой API-запрос, подмену ID, повтор запроса или обход интерфейса.

OBJECT-LEVEL SECURITY

Проверка каждого объекта

Доступ к одному делу не даёт доступа к соседнему делу, другому проекту, другому партнёру или чужому активу.

AUDITABILITY

Проверяемый след

Успешные, отклонённые и административные операции фиксируются с субъектом, временем, объектом, результатом и correlation ID.

03 / ПРОТОКОЛ РЕЗУЛЬТАТОВ

От теста — к доказательству.

У каждого запуска должны быть версия приложения, commit SHA, среда, тестовые данные без реальных персональных сведений, исполнитель и итог.

Поле протоколаЧто фиксировать
Test Run IDУникальный идентификатор запуска
Build / CommitТочный SHA сборки и версия спецификации
EnvironmentИзолированный тестовый контур, конфигурация без секретов
ResultPASS / FAIL / BLOCKED, фактический и ожидаемый результат
EvidenceСсылка на обезличенный лог, отчёт или скриншот теста
ApprovalОтветственный проверяющий и дата решения о допуске

Текущий статус: сценарии описаны как требования. Это не означает, что тесты уже запускались или пройдены: backend и тестовый контур в рамках этой работы не подтверждены.
